# 第一步规划

**我现在先建立单 UE 的统一时延测量基线：先准备测量程序，再比较 ping 和 UDP 的小、中、大包，最后确定后续实验使用的测量方法。**

当前状态：A 准备与 B 六条件短测已通过；六条件正式对照尚未执行。原 256 B / 80 B 测量头 / 指数间隔 UDP 三轮结果保留，所以第一步整体仍为“部分完成”。2026-11-12 已实际启动独立核心网、gNB、UE 完成短测，结束后资源回收。

## 我的第一步目标

我的研究对象是通信时延。汽车零部件装配提供应用背景，当前用可控请求—响应表示终端的信息交互，不处理视频内容或机械臂动作。

```text
UE 发送请求 → gNB → 核心网/UPF → 回复端
UE 收到响应 ← gNB ← 核心网/UPF ← 回复端
```

我在这一步回答三个问题：

- 相同无线条件下，56、256、1200 B 的包，通信往返时延分别是多少？
- 条件统一后，ping 与 UDP 的结果有多大差异，差异可能来自哪些计时和回复处理环节？
- 后续多 UE、TDD、SCS、分层和尾时延实验，该固定哪套测量程序与业务参数，才能相互对照？

我统计的是**请求到对应回复的通信 RTT**。机械臂动作完成时间和完整控制闭环不在当前计时范围内。

## 我先做六种条件

|数据长度 L|ping|UDP 请求—响应|无选项、无分片 IPv4 的内层 IP 包长|
|---|---|---|---|
|56 B：小包|ICMP 数据 56 B|请求与响应各 56 B|两者均为 84 B|
|256 B：中等包|ICMP 数据 256 B|请求与响应各 256 B|两者均为 284 B|
|1200 B：较大包|ICMP 数据 1200 B|请求与响应各 1200 B|两者均为 1228 B|

B 是字节。表中 L 是 ICMP 或 UDP 的数据长度，不包含各自 8 B 的头和普通 IPv4 的 20 B 头；内层 IP 按 L + 28 B 记账，不包括外层隧道和无线协议开销。实际是否分片仍要查 MTU 和抓包。

UDP 三档统一使用精简的 16 B 事务标记，标记包含在 L 内，其余为填充；不能小包用新探针、大包用旧 80 B 探针。ping 的计时字段与填充沿本机工具实现，内容不与 UDP 完全相同。

我选 56 B 方便对照常见 ping，256 B 衔接已有研究，1200 B 观察较大包。**这三档是我的实验设计，不是 3GPP 强制的工业包长，也不是机械臂实采数据。** 本步先做 ICMP 和 UDP；TCP 留到实际业务需要时单独安排。

## 我保证哪些条件一致

我先固定 1 UE、120 kHz 的已验证工作点。核心网、gNB、UE、RFsim、源码、二进制、绑核和观察方式都记录并冻结；无真实射频。

|项目|本轮固定安排|
|---|---|
|无线资源|n261、100 MHz、66 PRB、正常 CP、MCS 上限 9；不是每个传输块恒定 MCS 9|
|TDD|周期 0.625 ms：3 个完整 D、1 个混合槽、1 个完整 U；混合槽 6D + 4F + 4U；完整槽 D:U 为 3:1，混合槽仍须计入|
|调度与授权|PF、既有 legacy 探测 F = 10 帧、SR = 40 槽 / offset = 3、业务 K2 = 4；既有配对私有 HOL 报告保持并单独说明|
|路径与 QoS|同一 UE 接口、同一 UPF 侧目标 IP / 网络命名空间；目标 5QI 9 / QFI 9，每种工具核实实际 NAS 与双向 N3|
|到达方式|固定周期，20 ms 目标间隔，即 50 次请求/秒；不等上个响应才发下个请求；保存实际发送间隔和错过目标时间的情况|

**相同包率不等于相同 Mbps。** 按 8 × L × 50 / 10⁶ 换算，三档每方向名义应用速率分别为 0.0224、0.1024、0.4800 Mbps；对应内层 IP 速率为 0.0336、0.1136、0.4912 Mbps。请求和响应合计另计两倍。大包同时增加负载，所以这一轮解释的是“固定请求频率下的包长表现”；后续需要时再补固定 Mbps 对照。

周期输入可能偏向部分无线相位，我会保留发送时刻并检查相位覆盖，不能把它当成随机到达或全部 TDD 相位。RFsim 的墙钟运行与无线时间推进分别观察，不默认二者实时一致。

## 我怎样计时，怎样读出结果

我保留两种口径，并在图表中分开标明：

|口径|起止点|怎样使用|
|---|---|---|
|工具自身 RTT|ping 的 ICMP 请求—回复；UDP 客户端发送—接收对应响应|先比较同一种工具内的包长影响，跨工具结果包含端点处理差别|
|共同 UE TUN 区间|同一 UE TUN 抓包中，请求离开—对应回复到达|作为共同边界辅助比较；仍包含网络和回复处理，不是纯空口|

```math
T_{\mathrm{UDP},k}=t_{\mathrm{client,recv},k}-t_{\mathrm{client,send},k}.
```

Linux 内核处理 ICMP 回显，当前 UDP 由 Python 应用回显；我不会把跨工具的全部差异归因于无线调度。共同抓包区间还需要完成解析适配和验证，不能冒称已经测到。

UDP 另保存服务端接收与回复时刻，以支持后续上下行分段。分段先核时钟域与事务标识，抓包 REALTIME 和应用 MONOTONIC 不能直接相减；总 RTT 的 P99 直接从每个事务计算，不把分段 P99 相加。术语见[通信与时延基础知识](../算法知识点说明/00_通信与时延基础知识.md)。
