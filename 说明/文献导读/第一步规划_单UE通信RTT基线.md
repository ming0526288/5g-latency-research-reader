# 第一步规划

状态：部分完成。原 256 B、80 B 测量头、指数间隔的三轮 UDP 基线已完成；2026-11-12 新增的 ping / 精简 UDP 六条件对照尚未执行。本次只规划，不启动实验。

## 我的第一步目标

我先用 **1 个 UE，比较 ping 和 UDP，各测 56、256、1200 B**。我要弄清：相同无线条件下，包长怎样影响每种测法的 RTT，以及两种测法的差异有多大。我的背景是汽车零部件装配中的状态信息交互，这一步用合成通信业务，不接入视觉处理或机械臂动作，不实现新调度算法。

```text
UE 请求 → gNB → 核心网/UPF → 回复端
UE 收到 ← gNB ← 核心网/UPF ← 回复端
```

## 我先做六种条件

|数据长度 L|ping|精简 UDP|普通 IPv4、无选项且无分片时的内层 IP 包长|
|---|---|---|---|
|56 B：小包|ICMP 数据 56 B|UDP 数据 56 B，含 16 B 标记|两者均为 84 B|
|256 B：中等包|ICMP 数据 256 B|UDP 数据 256 B，含 16 B 标记|两者均为 284 B|
|1200 B：较大包|ICMP 数据 1200 B|UDP 数据 1200 B，含 16 B 标记|两者均为 1228 B|

B 是字节。UDP 请求和响应的数据长度都取 L；ICMP 头和 UDP 头均另占 8 B，普通 IPv4 头另占 20 B，所以上表按 L + 28 B 记账，不包含 GTP-U、外层 IP 或无线协议头。执行时还要检查 MTU 和实际分片。ping 的计时内容与 UDP 标记不同，包内容并不完全一样。

56 B 便于对照常见 ping，256 B 衔接已有实验，1200 B 观察较大包；**这是我的工程取值，不是 3GPP 指定的工业包长，也不是机械臂实采业务。** 本步先不加 TCP，以后实际业务需要时再补。

## 我固定哪些条件

|条件|我的安排|
|---|---|
|平台|独立 5GC 副本 + gNB + 软件 UE + RFsim，同一主机，无真实射频|
|无线与版本|冻结已验证源码、二进制和配置；n261、100 MHz、66 PRB、120 kHz、正常 CP、MCS 上限 9|
|TDD|0.625 ms 周期：3 个完整 D + 1 个混合槽 + 1 个完整 U；混合槽 6D + 4F + 4U；完整槽 D:U 为 3:1，不能忽略混合槽|
|调度与授权|固定 PF、既有 legacy 探测 F = 10 帧、SR = 40 槽 / offset = 3、业务 K2 = 4；既有配对私有 HOL 报告保持并标明身份|
|业务路径|两工具使用同一 UE 接口和同一 UPF 侧目标 IP / 网络命名空间；核验路由和双向 N3，排除同机旁路|
|QoS|目标沿用 5QI 9 / QFI 9；每种工具均实际核 NAS / N3，不能假定 ICMP 与 UDP 自动相同|
|请求间隔|两者固定 20 ms 目标间隔，即 50 次请求/秒；不等待上一条回复；保存实际发送间隔和逾期情况|
|运行条件|相同绑核、线程策略、后台与观察开销；记录实际落核、抓包丢弃和 RFsim 推进|

固定 50 次/秒时，56、256、1200 B 的每方向名义应用速率分别为 **0.0224、0.1024、0.4800 Mbps**，按 8 × L × 50 / 10⁶ 换算。对应内层 IP 速率为 0.0336、0.1136、0.4912 Mbps；请求与响应合计另计两倍，不能混用。固定包率时，大包同时带来更大负载；需要分离负载影响时再补固定 Mbps 对照。

固定周期可能偏向部分无线相位。我会记录发送时刻、检查相位覆盖；本轮不能代表随机到达或全部 TDD 相位，RFsim 墙钟时间也不能默认等于标称无线时间。

## 我按什么顺序做

1. **先补准备。** 精简 UDP 已有 16 B 标记与本地四时刻，但当前仍为指数间隔，没有固定周期选项；旧全栈 N3/TUN 解析器仍依赖 80 B 格式。后续先实现周期输入和新 UDP / ICMP 事务关联，再做自测。本次不改这些程序。
2. **再做先导。** 六条件各计划 200 次请求，前 20 次预热；核验接入、路径、QoS、时钟、实际间隔和包长。先导不计入正式结果；失败保留证据并说明测到哪里。
3. **最后做正式对照。** 每条件重复 3 轮，每轮 2200 次请求、前 200 次预热、后 2000 次统计，共 **18 次正式运行**。顺序预先交错安排并记录，每次只跑一种测试业务；退出与最后回复等待规则在运行前冻结，不为通过而放宽门槛。

若全部成功，共发送 39600 次请求，去预热后最多统计 36000 次完整事务。这是计划数量，不是已测结果。逐轮报告有效、缺失和超时，不混池、不删除慢包；当前样本用于描述性 P99，不认证 P99.9 或长期可靠性。

## 我怎样计时和比较

**工具自身 RTT：** ping 的 ICMP 请求—回复 RTT；UDP 的客户端应用发送至对应响应接收 RTT：

```math
T_{\mathrm{UDP},k}=t_{\mathrm{client,recv},k}-t_{\mathrm{client,send},k}.
```

Linux ICMP 回复与当前 Python UDP 回显的处理路径不同。我先在同种工具内部比较包长，跨工具差异不能全部归因为无线调度。

**共同抓包区间：** 计划在同一 UE TUN 抓包内，统计同一事务请求离开至回复到达。ICMP 用标识 / 序号、UDP 用 UE / run / seq 关联，并核验双向 N3；该区间仍含网络与回复处理，不是纯空口。这是待实现、待验证的辅助口径。

UDP 另记录服务端接收与回复时刻。上下行分段先核时钟域；抓包 REALTIME 与应用 MONOTONIC 分开处理，不能直接相减。总 RTT 的 P99 从事务直接计算，不把分段 P99 相加。概念见[通信与时延基础知识](../算法知识点说明/00_通信与时延基础知识.md)。
