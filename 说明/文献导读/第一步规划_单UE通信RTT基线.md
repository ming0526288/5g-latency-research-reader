状态：已完成。2026-11-11 完成单 UE 新全栈基线与独立统计复核；实际结果见对应结果页。

## 我的第一步目标

我先建立“单 UE、固定无线配置、PF 调度”的通信 RTT 基线，获得后续对照的参照结果。这一步只验证通信场景和测量方法，暂不实现新的优化算法。

我的应用背景是汽车零部件装配中的状态信息交互。我先用可控请求—响应业务表示这类通信，不接入机械臂动作或视觉识别算法。

```text
UE 发出带事务编号的 UDP 请求
    → gNB → 核心网/UPF → 服务端收到
    → 服务端返回同一事务的响应
    → 核心网/UPF → gNB → UE 收到响应
```

## 我会先确定哪些条件

|项目|我的安排|
|---|---|
|网络和版本|沿用 OAI 核心网、gNB、UE、RFsim；执行前冻结修正后的源码、二进制与配置。|
|UE 数量|先用 1 个 UE。|
|无线工作点|先核对并固定已验证的 120 kHz 工作点，完整记录频段、带宽、TDD、TDA/K2、SR 等配置。|

|业务输入|确定请求和响应包长、发包规律、低负载起点及 QoS；已固定为请求/响应各 256 B、指数目标间隔均值 20 ms、每方向目标 0.1024 Mbps；新 NAS 确认 5QI 9 / QFI 9。|
|统计规则|三轮不同种子，各 2200 事务/前 200 预热；共 6000 统计事务；客户端 100 s / 服务端 105 s，缺失/失败保留。|

这些是我的实验设计安排，不是 3GPP 强制的一套业务参数。我已冻结场景表并按表完成运行；完整无线、版本、授权和计时条件写在对应结果页。

## 我怎样计时和验收

我为同一事务关联 UE 发出、服务端收到、服务端发出响应、UE 收到四个时刻。RTT 从 UE 发请求计到 UE 收到对应响应；服务端响应处理单独记录，不默认等于 0。

```math
T_{\mathrm{RTT},k}=t_{\mathrm{UE,recv},k}-t_{\mathrm{UE,send},k}.
```

我会核验业务确实经过 OAI 网络，排除同机旁路；核验包编号、时钟和计时边界；重复运行后统计 RTT 中位数、P95、P99，以及响应完成、丢失和未完成情况。上下行分段需另核两端时钟，不用 RTT 冒充单向时延，也不把分段 P99 相加。

我将以路径正确、数据关联正确、统计可复现作为这一步的完成条件，不预先承诺某个毫秒值或优化收益。
