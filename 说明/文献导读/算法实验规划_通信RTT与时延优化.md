# 算法实验规划

更新：2026-11-12。主线第一步当前 UDP256 B 基线已建立，引用独立实验 E-MEAS-01 的三轮同版本数据（6600完整/6000统计），不增加运行次数。源码/包头/ping与工具对照单独归档，不占主线十二步。

## 1. 我的研究目标与计时范围

我的应用背景是汽车零部件装配工作站中的多终端通信，实验室机械臂组装小车提供缩比背景。我主要研究多个 UE 竞争资源时，怎样降低通信往返时延 RTT，尤其是 P99，同时检查上行、下行、丢包和资源开销。

我先搭建可重复的通信业务场景，沿用现有 OAI 核心网、gNB、UE 和 RFsim。机械臂动作、视觉识别和控制算法不纳入这轮优化范围。

```text
UE 发出带事务编号的请求
    → gNB → 核心网/UPF → 服务端收到
    → 服务端生成对应响应
    → 核心网/UPF → gNB → UE 收到响应
```

我将“闭环”限定为这一次请求—响应的通信往返，在论文和结果页中统一称为“应用层通信往返时延 RTT”。我不把它称为已经验证的机械臂控制闭环。

```math
T_{\mathrm{RTT},k}=t_{\mathrm{UE,recv},k}-t_{\mathrm{UE,send},k}
=T_{\mathrm{UL},k}+T_{\mathrm{reply},k}+T_{\mathrm{DL},k}.
```

各量对应同一事务，时间单位统一为 ms。RTT 包含实际经过的协议栈、网络、主机和响应处理。我会直接统计每轮总 RTT 的 P99，不将各段 P99 相加。响应处理单独记录，不假定为 0。RTT 起止由同一 UE 时钟记录；上下行分段还要核对两端时钟及包关联。

## 2. 主线当前基线与下一步

第一步只保留固定版本/配置的单UE UDP基线，详见[第一步规划](第一步规划_单UE通信RTT基线.md)。我引用已经核验的256 B请求/响应、20 ms目标周期三个条件；该数据来自同一次已完成运行，不包装成新实验。

随后增加2、3个UE，先相同QoS，分别比较同总负载与同每UE负载，再完成TDD、SCS、分层和尾时延五类分析。瓶颈明确后再选择优化算法。

源码、原始版本复测、测量字段与ping等工具研究在[独立测量实验](../研究结果与分析/独立实验_原始版本ping与包头对照.md)，配套[独立知识页](../算法知识点说明/测量方法与包头对比_知识点分析.md)。它与本路线分开，主线只引用方法与基线结论。

## 4. 五类分析我都保留

|分析|我要回答的问题|
|---|---|
|TDD 配比和周期|UL 机会增加后，上行是否更快，返回响应是否反而等待更久？|
|SCS|槽更短后，RTT 是否降低，还是被处理、资源量、分段和重传抵消？|
|多 UE|竞争使哪些 UE 的 RTT 恶化，原因是资源、队列还是主机推进？|
|分层时延|同一事务在上行等待、传输/重组、响应处理和下行分别停留多久？未测部分明确标记。|
|尾时延|P99 慢事务由什么事件触发，优化后是否只是将等待转移给其他事务？|

TDD 的 3:1、2:2、1:3 等简称要配完整周期、D/U 槽、其余符号、TDA/K2 和控制/反馈配置；它们是按标准字段构造的实验方案，不是协议逐项列举的强制配比。

我先在 n261 的合法可运行工作点比较 60/120 kHz；30 kHz 使用支持它的 FR1 配置。240 kHz 单列频段/实现支持边界或模型分析，不直接作为 n261 数据配置。跨频段的差异不全部归因于 SCS。RFsim 墙钟时间与无线槽标签分别记录，不假定其始终实时推进。

## 5. 我怎样选择优化算法

我先定位瓶颈，再决定完整算法，不预先承诺时延下降比例。

|观察到的主要等待|我的候选方向|依据和边界|
|---|---|---|
|有积压的 UE 长时间得不到有效服务，或一包跨多次授权才发完|积压与有效服务间隔感知调度|结合新版本慢包证据设计；QUEST 提供 QoS/等待信息的调度对照，但这不是某篇已读论文的完整现成算法。|
|首包主要等待请求和授权|资源预算约束的提前授权|参考 AUGUSTE 的授权时机思想；只有存在可利用的到达规律或可见触发时，才研究预测器，并保留随机负对照。|

旧数据提示积压服务值得优先核验，我会先用新基线确认。PF 是通用参照，EDF、M-LWDF、QUEST 是时延/QoS 强对照；它们不是 3GPP 指定的唯一调度方案。使用 HOL 等额外报告时，我会让所有对照具有相同信息路径和开销，明确私有扩展的身份。

## 6. 我怎样判断“通信时延变小了”

我在相同场景、输入计划、程序版本、探针和统计口径下做配对重复，报告每 UE 的 RTT 中位数/P95/P99、上行/下行分项、响应完成与丢失情况，以及无线资源和调度代价。

“比基线更小”和“满足业务期限”是两个问题。我会在声明业务期限后，按全部生成请求计算期限内完成比例；丢失、超时和未完成事务不从分母中删去。仅已收到响应的 RTT P99 改善，不足以单独证明整体收益。

我先在一个可靠工作点验证机制，再扩展 TDD、SCS、UE 数和负载。调参与正式评估输入分开；独立种子、运行顺序、预热和样本量预先记录。真实射频、机械臂动作和产线效率仍属于后续验证边界。
