# 100 到 200 MHz 单 UE 时延方案三（优化上下行发送机会）

**200 MHz、单 UE、门限 0 下，慢包主要慢在上行。** 五轮常规短测中，最慢 10% 的 ping 多出的往返时延约 71% 在上行。新增的一轮逐包诊断进一步发现，慢包多出的上行时间约 **80% 在等 UE 拿到实际用来承载这个包的授权**。调整 TDD 时，候选图样在方案 A 下三次停在初始同步前。启用方案 B 后已接入并完成 56 B ping，两轮平均 RTT 均高于同构建的原图样。 [调整 TDD 结果](方案三的第二种_调整TDD.md)

三种做法按改动位置划分。共用业务基线为 **56 B ping**，每次先单独验证一项。以下是已有 ping 的慢包定位。

## 慢包多出的时间在哪一段

我复算了五轮既有短测。各轮都是 200 MHz、n261、120 kHz、132 PRB、5 槽 TDD、单 UE、门限 0、56 B ping，目标间隔 20 ms。每轮 200 发／200 收，去掉前 20 个预热包。按 UE 虚拟网卡（TUN）上看到的往返时间，在每轮各取最慢 18 个包，与同轮另外 162 个包比较。这样每轮都有自己的参照。表中单位为 ms，取五轮同类包的平均。

| 比较组 | 上行请求（UE TUN → 基站 N3） | 核心网侧（N3 请求 → N3 回复） | 下行回复（基站 N3 → UE TUN） | TUN 处往返 |
| --- | ---: | ---: | ---: | ---: |
| 最慢 10%（90 个） | 0.991 | 0.063 | 0.633 | 1.687 |
| 其余 90%（810 个） | 0.694 | 0.058 | 0.518 | 1.270 |
| 慢包平均多用的时间 | **0.297** | 0.005 | 0.115 | **0.418** |

每轮最慢组的额外时间都以上行为主，各轮上行占增量的 63%–88%。比如带宽回切中的 200 MHz 一轮，最慢的第 190 个 ping 在 TUN 处往返用了 2.170 ms，其中上行 1.166 ms、核心网侧 0.091 ms、下行 0.914 ms。上行和下行用的是同一个请求和回复的时间戳，四舍五入前逐包相加与 TUN 往返一致。

改用 ping 命令报出的往返时间排序，上行占增量约 72%。只看每轮最慢 5%，约 71%。另外三轮开启只读诊断的默认采样短测约 73%，方向也一致。八轮共复算 1,440 个统计包，每轮分开判断。这里复用了既有抓包，没有新发包。

N3 路径及抓包识别依据见 TS 38.300 V19.4.0 §4.3.1.1、TS 29.281 V19.2.0 §5.1、§5.2.1、§5.2.2.7 和 TS 38.415 V19.1.0 §5.5.2.1、§5.5.2.2、§5.5.3.3。

逐轮汇总保存在本目录下的 `数据/第二步_200MHz单UE门限0_ping慢包方向_20261120.json`。

## 上行里具体慢在哪一步

我沿用原 200 MHz、单 UE、门限 0、56 B ping 和五槽图样，只开启已编入程序的只读探针。复测 200 发／200 收，前 20 包预热，全部请求逐包匹配到原有授权、同一个上行传输块和基站成功接收。按 TUN 往返重取最慢 18 个包，与其余 162 个比较。表中是 RFsim 的主机计时，单位为 ms。

| 上行分段 | 最慢 18 个包 | 其余 162 个包 | 慢包多用 |
| --- | ---: | ---: | ---: |
| 包入队后，等 UE 确认实际用到的授权 | 0.326 | 0.098 | **0.228** |
| 授权和包都已就绪，到目标槽开始取包组装 | 0.109 | 0.089 | 0.020 |
| UE 编码完成，到基站收到并报告校验通过 | 0.442 | 0.407 | 0.035 |
| 其余栈内处理合计 | 0.080 | 0.079 | 0.001 |
| **上行合计** | **0.957** | **0.674** | **0.283** |

**0.228 ms 的授权等待增量中，有 0.207 ms 来自包入队后与「基站准备授权 → UE 接受授权」重叠的部分。** 这批慢包里，包先入队，然后 UE 才收到第一条可用来承载该包的授权。其余 162 包中有 57 包入队前已经收到本包随后用到的授权，因此这一段计为零。最慢的第 130 个包在 TUN 处往返 2.328 ms，其中上行 1.760 ms，包准备好后到接受授权用了 1.110 ms。

180 个统计包的**授权槽到数据目标槽都相隔 4 槽**，在 120 kHz 网格上是 0.500 ms 无线时间。上表第二行看的是主机上到目标槽的组装回调，探针在组装和编码边界取戳。第三行仍包含编码后的发送准备、RFsim 样本推进和基站接收处理。现有记录还不能把「基站准备到 UE 接受」拆成控制信令发送前排队、RFsim 推进与 UE 解码各自的耗时。按上行时间重新排序，授权前的增量仍是最大的。

第一轮也收齐 200 个回复，但持续的空闲授权记录在发包前填满了基站 MAC 和 UE PHY 探针，逐包链路未闭合。复测缩短了接入后到发包的间隔，链路记录齐全。分段表来自一轮开探针的复测，现阶段用于定位主要增量，尚未做同批探针开关的重复对照。安全汇总保存在本目录下的 `数据/第二步_200MHz单UE门限0_ping授权分段_20261120.json`。

授权内容和时域位置依据 TS 38.212 V19.4.0 §7.3.1.1.1／§7.3.1.1.2、TS 38.214 V19.5.0 §6.1.2.1、§6.4、TS 38.321 V19.4.0 §5.4.1／§5.4.2。包通过 SDAP、PDCP 和 RLC 的关联依据 TS 37.324 V19.0.0 §5.2、§6.2.2.3，TS 38.323 V19.1.0 §5.2.1／§5.2.2，TS 38.322 V19.3.0 §5.2.3.1、§6.2.2.4。探针位置和记录格式是本项目的测量方法。

## 业务到达时刻如何影响授权等待

**0.207 ms 衡量的是包已经入队以后，落在「基站准备授权 → UE 接受授权」区间内的平均额外等待。** 如果这段在包入队前已经走完，包在这段的等待就是零。用同一批包复算准备到接受的完整耗时，最慢 18 包为 **0.350 ms**，其余 162 包为 **0.272 ms**，相差 **0.078 ms**。因此，除了控制链路本身的耗时，还要看包到达时授权已经走到哪一步。

| 口径 | 最慢 18 包平均 | 其余 162 包平均 | 差值 |
| --- | ---: | ---: | ---: |
| 基站准备授权 → UE 接受授权的完整主机时间 | 0.350 ms | 0.272 ms | 0.078 ms |
| 只统计包入队后的重叠时间 | 0.305 ms | 0.097 ms | 0.207 ms |

180 个包实际用到的授权都在周期内**槽 0**，目标数据都在**槽 4**。旧带宽回切的诊断轮也是同样的位置。100 MHz 的 20,164 条和 200 MHz 的 8,075 条基站授权准备记录，都标记为槽 0 → 槽 4。旧数据核对的是基站准备的授权，最新数据逐包核对了 UE 确认授权和基站收到的数据。这里按每个 5 槽周期从 0 编号，即第 1 槽授权、第 5 槽发上行数据。 [旧带宽回切结果](100到200MHz单UE时延变化的原因.md)

同一包的上行和下行机会都要放回完整的 RTT 看。各方案用同样的业务口径，并将无线槽差和 RFsim 主机时间分别记录。方案二的 CG Type 1／Type 2 说明 UE 怎样获得并启用可周期复用的上行授权。此处三个方向都可以从现有门限 0 的动态授权基线起步。[方案二（配置授权 CG）](100到200MHz单UE降低时延方案二_配置授权CG.md)
