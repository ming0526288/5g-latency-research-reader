# 方案三的第三种（调整调度时序）

我先固定 `D D D S U` 的 TDD 图样，再检查**基站在哪个下行位置发出控制指令、指向哪次数据发送**。上行看 `K2`，也就是授权槽到上行数据目标槽的偏移。下行看 `K0`，也就是下行调度指令到下行数据目标槽的偏移。

| 例子 | 授权所在槽 | 上行数据目标 | 怎么理解 |
| --- | ---: | --- | --- |
| 现有实测 | 槽 0 | 本周期槽 4 | `K2 = 4`，逐包确认。 |
| 只把授权移一槽 | 槽 1 | 下一周期槽 0 | 若仍用 `K2 = 4`，目标落在全下行槽。 |
| 时序候选 | 槽 1 | 本周期槽 4 | `K2 = 3` 在槽位上对得上，仍需核验 UE 监听和处理时间。 |

现有实现配置为 `min_rxtxtime = 4`。候选首先要检查 UE 在槽 1 是否监听 PDCCH（下行控制信道），以及从收授权到准备发送 PUSCH（上行数据物理信道）是否来得及。两个可行的授权若都指向同一个槽 4，发数据时间相同。时延能否下降，要看调度时序是否让原本错过机会的包用上更早的一次传输。

我会固定 **56 B ping** 的发包条件和 TDD 图样，分开观察三段时间：基站准备到实际提交控制样本、UE 取得样本到接受授权、接受授权到进入目标槽。验收时同时比较上行、下行、往返 P99、接入和空授权占用。上面在原图样里把授权移到槽 1 的安排仍待验证。

## 让候选图样的槽 3 真正发数据

固定 `D D S U U` 和方案 B 的 RFsim 启动方式。沿用基站已经能在槽 0 发出的授权，让 UE 在槽 3 发上行，对应业务 `K2 = 3`。基站用 UE 专用的 PUSCH 时域分配告知终端这一偏移。当前软件 UE 原来要求偏移严格大于 3 槽。研究副本只在配对 RFsim 试验里允许等于 3，利用同一轮里先处理下行控制、再提交上行发送任务的执行顺序。公共随机接入与下行反馈配置沿用原值。

120 kHz 下 3 槽约为 375 μs。这个配置的专用控制信道从槽首开始，占 1 个符号。按本机构建样本数保守估算，从控制符号末尾到槽 3 首符号约有 365 μs，尚未扣除定时提前。TS 38.214 V19.5.0 §6.4 表 6.4-1 的能力 1 基础量为 36 个符号，约 321 μs。若首个上行符号并非纯参考信号，再计 1 个符号，约 330 μs。这个预算用来筛选本次候选。实际余量仍取决于定时提前和标准规定的其他适用修正项，不能推广为所有硬件都支持。

## 56 B ping 实测

用同一对 gNB 和 UE 程序固定 200 MHz、120 kHz、单 UE、门限 0、0.625 ms 周期及 `D D S U U`。按 K2=3 → K2=4 → K2=3 → K2=4 运行。每轮 200 发、200 收，去掉前 20 包。上、下行通过 TUN/N3 同包关联，RTT 用原生 ping。

| --- | ---: | ---: | ---: | ---: |
| K2=3 第 1 轮 | 1.483 ms | 2.001 ms | 0.713 ms | 0.692 ms |
| K2=4 第 1 轮 | 1.617 ms | 2.208 ms | 0.883 ms | 0.653 ms |
| K2=3 第 2 轮 | 1.496 ms | 2.121 ms | 0.691 ms | 0.725 ms |
| K2=4 第 2 轮 | 1.663 ms | 2.351 ms | 0.915 ms | 0.664 ms |

两轮平均 RTT 从 **1.640 ms 降到 1.490 ms**，减少约 **0.151 ms（9.2%）**。平均上行约减少 0.197 ms，下行约增加 0.050 ms。从授权到目标槽的偏移缩短 1 槽，相当于 0.125 ms，应用往返还包含排队、下行等环节。

**槽 3 已实际承载业务。** K2=3 第一轮的 180 个统计包逐包关联到 UE 接受授权、实际发送和基站成功接收。其中 **143 个由槽 0 授权、槽 3 发送**，另外 **37 个由槽 1 授权、槽 4 发送**。K2=4 两轮的 360 个统计包全部是槽 0→槽 4。K2=3 第二轮的部分槽位探针提前写满，应用 RTT 和 TUN/N3 抓包完整。结论限本机单 UE 短测条件，真实射频和多 UE 尚未验证。 [第二种的槽位证据](方案三的第二种_调整TDD.md)

依据为 TS 38.213 V19.5.0 §10.1、§11.1，TS 38.331 V19.4.0 §6.3.2 的 `SearchSpace` 和 `ControlResourceSet`，以及 TS 38.214 V19.5.0 §5.1.2.1、§5.3、§6.1.2.1、§6.4。时域分配参考教材 §6.4.3（本地 PDF 第 211–213 页）。[38.213 版本](https://portal.3gpp.org/desktopmodules/Specifications/SpecificationDetails.aspx?specificationId=3215) · [38.214 版本](https://portal.3gpp.org/desktopmodules/Specifications/SpecificationDetails.aspx?specificationId=3216) · [38.331 版本](https://portal.3gpp.org/desktopmodules/Specifications/SpecificationDetails.aspx?specificationId=3197)

## 同一个 ping 回复在哪一段变慢

我固定 200 MHz、120 kHz、单 UE、门限 0、0.625 ms 周期和原生 56 B ping，目标发包间隔为 20 ms。三组共用同一套 gNB、UE 和 RFsim 程序，按 A → B → C → C → B → A 回切。每轮发 200 包、收 200 个回复，前 20 包只用于预热。六轮共完成 1,200 个逐包匹配，统计使用 1,080 个。

| 组别 | 周期内槽图样 | 上行授权偏移 | 原生 ping 平均 RTT | 平均上行 | 平均下行 | 两轮下行 P99 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| A | D D D S U | K2 = 4 | 1.319 ms | 0.710 ms | 0.528 ms | 0.621–0.628 ms |

| --- | ---: | ---: | ---: |

| 进入队列 → 基站首次查询这条队列 | 0.070 | 0.070 | 0.113 |
| 首次查询 → 基站确定该 UE 的下行分配 | 0.002 | 0.002 | 0.003 |
| 确定下行分配 → 基站开始向 RFsim 写入该槽样本 | 0.099 | 0.086 | 0.096 |
| 开始写入 → UE 解码后交给 MAC | **0.315** | **0.424** | **0.478** |
| UE MAC → UE 的 TUN 收到回复 | 0.017 | 0.019 | 0.020 |

以 C 第一轮的第 100 个回复为例，从 N3 收到回复起算，基站在 **0.190 ms** 确定承载它的下行分配，在 **0.271 ms** 开始写入该槽的仿真采样，**0.707 ms** 时 UE MAC 拿到解码后的数据，**0.722 ms** 时回复到达 UE 的 TUN。基站调度、仿真写入和 UE 解码关联到第 339 帧的槽 40，对应周期内槽 0。所有统计包都在入队后的首次业务队列查询中获得调度。两包恰好在查询调用期间入队，同槽数据块确认该次查询已服务它们。三组下行调度和 PDSCH 数据都在同一槽，对应 K0 = 0。

**A → B 只改图样。** 下行平均增加约 0.097 ms，首次查询前的等待均值都约为 0.070 ms。主要增量出现在样本写出之后。单独看两组都发得最多的周期内槽 1，开始写入到 UE MAC 也由 0.310 ms 增至 0.419 ms，所以不同槽的包数占比只能解释一部分现象。

**B → C 只缩短上行 K2。** 上行平均少约 0.151 ms，下行平均多约 0.115 ms，其中首次查询前多约 0.043 ms，开始写入到 UE MAC 多约 0.054 ms。原生 ping 平均只少约 0.020 ms，两轮 RTT P99 都高于 B。C 的平均 RTT 仍比 A 高约 0.234 ms。

这轮 A、B、C 从基站写完到 UE MAC 的平均时间分别为 0.291、0.408、0.457 ms。下一段用新探针细分 A、B 的收样和处理时间，两组的 K0 与 K2 相同。

K0 和时隙方向按 TS 38.214 V19.5.0 §5.1.2.1、TS 38.213 V19.5.0 §11.1、TS 38.211 V19.5.0 表 4.3.2-1 核对。逐包配对参考 P01《Dissecting 5G New-Radio Latency》§III–IV（本地 PDF 第 2–4 页），用户面边界结合教材第 2 章（本地 PDF 第 49–55 页）。探针时间是主机单调时钟下的实测，0.125 ms 是 120 kHz 正常 CP 下的名义槽长。

## UE 等采样和解码各花多久

我保留 **D D D S U** 为基线 A，只回切已经验证过的候选 **D D S U U** 为 B。两组共用同一构建，固定 K0 = 0、K2 = 4、200 MHz、120 kHz、单 UE、门限 0、56 B ping 和 20 ms 目标间隔。按 A → B → B → A 测四轮，每轮 200 发、200 收。800 个回复的时间线全部配对，去掉每轮前 20 包后统计 720 个。

| 基站写完这一槽后，同一个回复还经历什么 | D D D S U / ms | D D S U U / ms |
| --- | ---: | ---: |
| 基站写完 → RFsim 判定当前读取需要的采样已齐 | **0.097** | **0.226** |
| 采样齐 → UE 读取函数返回 | 0.010 | 0.010 |
| 读取返回 → 完成控制处理、准备提交解码任务 | 0.011 | 0.011 |
| 提交任务 → 工作线程开始处理 | 0.003 | 0.003 |
| 工作线程开始 → 进入数据块解码 | 0.094 | 0.092 |
| 数据块解码调用 | 0.076 | 0.069 |
| 解码返回 → UE MAC 收到数据块 | 0.002 | 0.002 |
| 采样齐之后合计 | **0.196** | **0.186** |
| 基站写完 → UE MAC 合计 | **0.293** | **0.413** |
| 完整下行（基站 N3 → UE TUN） | 0.543 | 0.647 |
| 原生 ping 平均 RTT | 1.369 | 1.617 |

**增加的时间集中在采样齐之前。** 这一段增加 0.130 ms，其中 UE 进入读取函数之前多约 0.060 ms，进入后等驱动判定够读多约 0.070 ms。采样齐后的合计反而少了约 0.009 ms。解码调用的数字包含实现内部处理和等待。提交任务到工作线程开始的数字包含入队和派发。

当前 UE 主线程已经在前一次读取中拿到了本槽第一个符号。它随后读本槽剩余样本，并一并读下一槽第一个符号。两组所有统计回复的读取结束位置都超过了本次下行写入的末端。我按 RFsim 采样序号和长度，匹配使该读取满足条件的下一次基站写入。

| ping 回复的下行槽 | 回复数 | RFsim 等到哪一槽才够读 | 本槽写完 → 够读平均 |
| --- | ---: | --- | ---: |
| A 周期内槽 1（全下行） | 302 | 同周期槽 2 的下行采样 | 0.090 ms |
| B 周期内槽 1（全下行） | 296 | 同周期槽 2 的混合槽下行采样 | 0.218 ms |
| B 周期内槽 2（混合槽） | 37 | 跨过槽 3、4，等到下一周期槽 0 的采样头到来 | 0.300 ms |

B 的 37 个混合槽回复中，UE 要读的末端比该混合槽的下行突发多 19,727 或 19,855 个采样。这个末端落在下一周期槽 0 发样起点之前或恰好相等。RFsim 收到下一块的时间戳，才把中间未发送的区间推进过去。其余 323 个 B 回复等到相邻槽就够读。只比较两组最常用的周期内槽 1，B 仍多等 0.128 ms，这个现象不限于混合槽承载业务的少数回复。

以 B 第一轮第 22 个回复为例，它在第 392 帧的槽 7 发送，槽 10 的采样头到达后才够读。相对于基站写完槽 7，够读发生在 **308 μs**，解码完成在 **439 μs**，UE MAC 收到数据在 **441 μs**。这是 RFsim 的主机时间。K0 仍为 0，额外等待来自软件读取窗口跨到后续样本。下一段保持原图样作为基线，实测分开读取之后的收益。

时隙与符号取 TS 38.211 V19.5.0 表 4.3.2-1，TDD 方向取 TS 38.213 V19.5.0 §11.1，K0 按 TS 38.214 V19.5.0 §5.1.2.1。TS 38.214 §5.3 的处理时间用于 HARQ-ACK 时序。本页用软件探针，从实际采样和解码边界计时，结论限本机 RFsim。

## 把当前槽解码与下一槽预读分开

我在同一套 200 MHz、120 kHz、单 UE、门限 0 的 RFsim 程序上做了三组对照。每组两轮，每轮 200 个 56 B ping、目标间隔 20 ms，前 20 个作预热。六轮 1,200 个回复全部逐包匹配，统计使用 1,080 个。K0 固定为 0，K2 固定为 4。

| 条件 | 平均 ping RTT / ms | 平均上行 / ms | 平均下行 / ms | 基站写完 → 够读 / ms |
| --- | ---: | ---: | ---: | ---: |
| A，D D D S U，原读法 | 1.360 | 0.739 | 0.534 | 0.092 |
| B，D D S U U，原读法 | 1.574 | 0.861 | 0.633 | 0.222 |
| C，D D S U U，分段读法 | 1.491 | 0.871 | 0.539 | 0.106 |

**同为 D D S U U，分段后平均下行少 0.094 ms，平均 ping RTT 少 0.083 ms（约 5.3%）。** 改善主要来自提前拿到当前槽的样本。两轮 ping RTT P99 的变化一降一升，分别为 1.922 → 1.742 ms、2.016 → 2.104 ms。

原本 UE 会把当前槽剩余采样和下一槽首符号读齐，再启动当前槽工作。新读法在全下行槽先读到本槽末，在混合槽先读到第 6 个下行符号末。随后提交当前槽解码，再把其余样本读回原缓冲区位置。两次读取的绝对采样序号连续，长度之和与原读法一致。当前这批混合槽 PDSCH 从符号 1 开始、占 5 个符号，编号从 0 起，全部位于先读到的下行段内。上行工作仍在后半段读完后提交。

| D D S U U 的下行槽位置 | 原读法回复数 | 分段读法回复数 | 原读法基站开始发样 → UE MAC | 分段读法基站开始发样 → UE MAC |
| --- | ---: | ---: | ---: | ---: |
| 周期内槽 1（全下行） | 284 | 286 | 0.422 ms | 0.325 ms |
| 周期内槽 2（混合槽） | 42 | 28 | 0.436 ms | 0.169 ms |

表中的回复数按其实际承载的下行槽统计。C 的 360 个统计回复都由当前槽的样本满足第一段读取。28 个混合槽回复全部在后半段读取结束前交给 UE MAC。以 C1 第 89 个回复为例，UE 首次读 10,960 个采样，后半段读 19,728 个，两次共 30,688 个。以基站写完当前槽起算，UE MAC 在 0.172 ms 收到该回复，此时后半段仍在读取。

### 剩下的 0.131 ms 多在哪里

我复算原图样与分段候选各两轮的现有抓包和上行探针。原生 ping 平均 RTT 多 0.131 ms。按同一 TUN／N3 时间边界核对，上行 **多 0.132 ms**，下行多 0.005 ms，核心网侧的请求到回复短了 0.004 ms。三个抓包段相加是 TUN RTT，均值多 0.133 ms。原生 ping 和 TUN 抓包的计时边界略有差异。

| 上行的哪一段 | D D D S U / ms | D D S U U 分段 / ms | 增量 / ms |
| --- | ---: | ---: | ---: |
| UE TUN 进入发送路径 → RLC 入队 | 0.021 | 0.020 | −0.001 |
| UE RLC 入队 → 生成承载本包的上行 RLC 数据单元 | 0.223 | 0.273 | **+0.050** |
| UE RLC 组包 → 基站 RLC 收齐并交给上层 | 0.450 | 0.536 | **+0.086** |
| 基站 RLC 交付 → N3 看见上行包 | 0.046 | 0.042 | −0.004 |
| 上行合计 | **0.739** | **0.871** | **+0.132** |

最明显的是组包后到基站收齐，约占上行净增量的三分之二。组包后还有 UE 编码、RFsim 发样和基站接收处理。另有约 0.050 ms 花在组包前的排队和调度等待。

只有 A1 和 C2 的细探针覆盖了完整业务窗口。这两轮的 360 个统计请求均由周期槽 0 授权、槽 4 上行发送，K2 同为 4。其中「UE 编码结束 → 基站 CRC 校验通过」从 0.420 ms 到 0.539 ms，多约 0.119 ms。这是这两轮内最大的细分增量。A2 与 C1 的部分细探针在发包前写满，整组可确认到上表的 RLC 边界。这一段仍包含 RFsim 采样推进和基站译码，需要更细的标记才能各自计时。上行时域配置与授权参照 TS 38.214 V19.5.0 §6.1.2.1、TS 38.321 V19.4.0 §5.4.1。队列到交付的计时边界沿用本次逐包探针。

### 分段读取再配合 K2 = 3

我在同一份 **D D S U U** 配置上一直打开 UE 分段读取，并固定 K0 = 0，只回切业务上行授权的 K2。每个条件两轮，每轮 200 个 56 B ping，20 ms 目标间隔，前 20 包预热。200 MHz、120 kHz、单 UE、门限 0 保持相同。四轮完整抓包共 800 个回复，统计用 720 个。

| D D S U U，分段读取 | 平均 RTT / ms | 平均上行 / ms | 平均下行 / ms | 两轮 RTT P99 / ms |
| --- | ---: | ---: | ---: | --- |
| K2 = 4 | 1.470 | 0.861 | 0.531 | 2.086、2.111 |
| K2 = 3 | **1.365** | **0.705** | 0.576 | 1.881、2.123 |

K2 改为 3 后，平均 RTT 少 **0.105 ms（约 7.1%）**。上行少 0.156 ms，下行多 0.045 ms，核心网侧多 0.006 ms。上下行和核心网段用 TUN／N3 同包抓包，RTT 列用原生 ping。两轮 P99 一低一高。

在槽位探针完整的 K2 = 3 补采轮里，**138／180 个统计请求是槽 0 授权、槽 3 发出**，其余 42 个是槽 1 授权、槽 4 发出。我把实际 PUSCH 载荷和基站 CRC 校验成功记录逐包关联了。K2 = 4 的两轮共 360 个统计请求，都是槽 0 授权、槽 4 发出。K2 = 3 的另一轮在发包前写满部分槽位探针，业务抓包完整。K2 = 3 首次试跑另有抓包收尾超时，保留日志后单独补采。

K2 对应授权槽到目标 PUSCH 槽的偏移，按 TS 38.214 V19.5.0 §6.1.2.1、§6.4 及 TS 38.331 V19.4.0 §6.3.2 核对。两项机制已在本机 RFsim 同时生效。此前 D D D S U 的 1.360 ms 仍作为原图样参考。
