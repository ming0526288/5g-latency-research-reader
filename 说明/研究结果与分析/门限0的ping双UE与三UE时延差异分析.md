# 门限 0 的 ping 从双 UE 到三 UE，时延增加在哪里

**最后接入的终端主要慢在上行。** 交换接入顺序后，偏慢从 UE 3 转到 UE 1。完整的反序调度记录显示，前两台反复拿到主动探测机会，最后一台在有包待发、基站尚未收到其发送请求的这段时间，通常要自己等到一次请求机会才能继续。

## 双 UE 和三 UE 的 ping 基线

两组短测都是 120 kHz、56 B 数据区，每台目标每秒发 50 次，发 200 次，剔除前 20 次预热。双 UE 用原探测顺序，三 UE 用空闲探测后置。两组间终端数、总请求速率和探测顺序同时变化，所以用它们比较现象，再用同为三 UE 的正反序检验偏慢是否跟着接入位置走。

|门限 0 短测|终端|上行请求|核心网侧往返|下行回复|ping 平均 RTT|
|---|---|---:|---:|---:|---:|
|双 UE，原顺序|UE 1|1.072 ms|0.057 ms|0.568 ms|1.709 ms|
|双 UE，原顺序|UE 2|1.039 ms|0.056 ms|0.601 ms|1.707 ms|
|三 UE，后置|UE 1|1.365 ms|0.052 ms|0.811 ms|2.241 ms|
|三 UE，后置|UE 2|1.400 ms|0.037 ms|0.844 ms|2.292 ms|
|三 UE，后置|**UE 3**|**6.277 ms**|0.042 ms|0.856 ms|**7.187 ms**|

上行从终端业务虚拟网卡（TUN）到基站通向核心网的 N3 接口，核心网侧往返从 N3 收到请求到 N3 看到回复，下行从 N3 到 TUN。三段都按同一请求序号和同一宿主的抓包时钟计算，相加得到 TUN 侧往返。最右列是 ping 程序自身计时，计时边界略有差异。

在三 UE 的同一轮里，第三台的平均 ping 比前两台的平均多 **4.921 ms**，其中上行段差 **4.895 ms**。与双 UE 相比，前两台各多约 0.53 ms 和 0.58 ms，上行和下行都略有增加。

## 交换接入顺序验证

用同一个后置构建、相同的三个终端订阅和业务负载做两轮 200 次短测。每轮先逐台接入，三台都就绪后才开始并发业务。表格按终端身份排列，均值使用每台预热后的 180 个样本。

|接入顺序|UE 1 平均 RTT|UE 2 平均 RTT|UE 3 平均 RTT|最后接入者的上行均值|
|---|---:|---:|---:|---:|
|UE 1 → UE 2 → UE 3|2.395 ms|2.455 ms|**7.482 ms**|UE 3，6.481 ms|
|UE 3 → UE 2 → UE 1|**7.702 ms**|2.398 ms|2.341 ms|UE 1，6.698 ms|

两轮各台都是 200/200。三路业务的共同统计时段分别为 3.092 s 和 3.290 s。正序的基站 MAC 记录在业务前耗尽容量，丢弃 549,290 条记录。该轮的 ping、抓包和最后接入者的请求信号记录仍可使用。反序的基站调度记录完整，下面的逐轮判断用反序记录。

## 为什么后置以后最后一台还会慢

1. **后置优先处理的是基站已经知道的需求。** 包刚到终端时，基站可能还未收到调度请求（SR），也还不知道终端有数据排队。此时它仍按空闲探测的规则来分配主动发送机会。
2. **剩余探测仍按固定顺序分。** 反序测量中，最后接入的 UE 1 在计时包的上行期间有 **1,123 个调度轮次**因余量耗尽跳过探测。这 1,123 轮中，另外两台当轮各获一次没有 SR、没有已知待发量的探测授权。计数单位是调度轮，一个包可能跨多轮。
3. **主要等待出现在发出请求之前。** 反序最后一台有 135/180 个包的上行抓包时间达到 5 ms。这 135 个包里，从终端 MAC 首次记录有待发数据且请求挂起，到首次指示发送 SR，平均 **4.545 ms**。基站收到有效 SR 后，至观测到给这个请求的授权调度，平均 **0.710 ms**，本轮未观察到已有 SR 的调度轮再被空闲探测挤掉。

两轮记录到的 SR 配置均为 40 个时隙的周期，按 120 kHz 的时隙长度换算是 **5 ms**。前两台频繁拿到主动授权，新的业务包常能赶上这些机会。最后一台更常等 SR，因此即使接入恢复，业务上行仍偏慢。两组诊断短测说明了这个工作点的机制。轮换剩余探测名额是否能降低最慢一台的时延，需要后续单独验证。[三 UE 上行调度优化方案](三UE上行调度优化方案.md)
