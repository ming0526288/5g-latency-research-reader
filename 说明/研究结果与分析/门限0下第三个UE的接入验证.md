# 门限 0 下第三个 UE 为什么接不进来

在这套 120 kHz 仿真配置下，原调度顺序会让前两个终端（UE）的空闲探测先用掉同一轮的两个上行调度名额。即使第三个 UE 已向基站请求资源，也可能连续被跳过。我保留门限 0，将纯空闲探测放到已有请求和待发数据之后，三个 UE 都完成了接入，短 ping 各收到 20/20 个回复。切回原顺序，接入异常再次出现。

## 为什么两台可以，三台会卡住

空闲探测是基站在暂未收到数据需求时，主动给 UE 一个小的上行发送机会。门限 0 在本配置中让 UE 达到 5 个时隙的空闲资格时，就可以参与探测分配。5 个时隙对应 0.625 ms，实际是否授权仍由调度决定。

当前实现用 66 ÷ (4 × 6) 向下取整，得到普通上行调度每轮约 2 个 UE 名额。其中 66 是上行载波的 PRB 数，4 是代码采用的平均聚合等级，6 是每个 CCE 的 REG 数。两个 UE 时，两份名额可以分别服务两台终端。加入第三台后，如果遍历在前的两台每轮都先获空闲探测授权，后面的第三台就会被跳过。这里的两个名额属于当前实现的每轮估算，小区能同时接入的终端数要看多个轮次能否轮流服务。

我在原构建的门限 0 对照里，看到第三个 UE 的 SR 已在基站标记为待服务的 33,244 个调度轮次。其中 33,229 轮（99.95%），前两个 UE 当轮都在没有 SR、没有已知积压时获得探测授权，第三个 UE 则因名额耗尽被跳过。这个比例按基站调度轮次计算，一次 SR 可以跨多个轮次保持待服务。UE 侧实际两次达到 64 次的 SR 重试上限，随后反复发起随机接入。

## 怎样让三个 UE 接入

|实验条件|接入结果|56 B ping 连通检查|
|---|---|---|
|原构建、门限 0、原调度顺序|前两个 UE 有业务地址，第三个反复随机接入|三 UE 业务未开始|
|原构建、门限 1、原调度顺序|三个 UE 都完成接入|每个 UE 收到 20/20 个回复|
|同一试验构建、门限 0、空闲探测后置|三个 UE 都完成接入|每个 UE 收到 20/20 个回复|
|同一试验构建、门限 0、切回原顺序|第三个 UE 再次反复随机接入，随后基站在 Msg4 重传分配时退出|三 UE 业务未开始|

只改配置时，可用门限 1 建立三 UE 链路。要保留门限 0，本次跑通的做法是基站先处理已有待发数据或收到的 SR，最后再用剩余名额安排纯空闲探测。反向对照使用完全相同的试验二进制，只切回调度模式。它再次记录到第三个 UE 的 28,992 个待服务轮次中，有 28,990 轮在前两次空闲探测用完名额后被跳过，UE 四次达到 SR 重试上限。

原构建的门限 0 测到重复接入后主动停止。反向对照则记录到 Msg4 重传时，基站发现可分配的传输块装不下待发数据，触发断言，这解释了那轮基站退出的直接原因。原调度导致的 SR 长期未获服务，和 Msg4 重传处的退出，是排查中看到的两个阶段。

## 三 UE 每台 200 次短测

三个 UE 共同接入后，我用空闲探测后置的同一构建分别跑了 ping 和 UDP。每路请求的数据区都是 56 B，目标每秒 50 次。各 UE 发 200 次，前 20 次为预热，其余 180 次参与统计。

|业务|每 UE 发出／收到|UE 1 / 2 / 3 平均 RTT（ms）|UE 1 / 2 / 3 P99（ms）|
|---|---:|---:|---:|
|ping|各 200/200|2.241/2.292/7.187|2.868/3.493/11.700|
|UDP|各 200/200|2.542/2.549/7.984|3.452/3.596/14.013|

两轮均确认三路有共同统计时段，上下行在 TUN 与 N3 逐包对应，双向 QFI 均为 9。第三个 UE 两轮都完整收到回复，测得的平均 RTT 和 P99 仍高于前两个 UE。P99 每路只基于 180 个样本。正式三轮和长时稳定性尚待测量。[短测数据](数据/第二步_门限0_空闲探测后置_3UE_200次短测_20261119.json)。

## 门限 0 的 ping 慢在哪一段

我用门限 0 的 ping 作基线。单 UE 正式均值 0.820 ms 用来参考。下表只比较每台发 200 次、前 20 次预热、56 B 数据区、每台目标每秒 50 次的双 UE 和三 UE 短测。两组分别使用原探测顺序和空闲探测后置，同时也改变了终端数和总业务量。

|实验组|终端|上行请求（TUN 到 N3）|核心网侧往返（N3 到 N3）|下行回复（N3 到 TUN）|ping 平均 RTT|
|---|---|---:|---:|---:|---:|
|双 UE，原顺序|UE 1|1.072 ms|0.057 ms|0.568 ms|1.709 ms|
|双 UE，原顺序|UE 2|1.039 ms|0.056 ms|0.601 ms|1.707 ms|
|三 UE，后置|UE 1|1.365 ms|0.052 ms|0.811 ms|2.241 ms|
|三 UE，后置|UE 2|1.400 ms|0.037 ms|0.844 ms|2.292 ms|
|三 UE，后置|**UE 3**|**6.277 ms**|0.042 ms|0.856 ms|**7.187 ms**|

TUN 是终端用来收发业务的虚拟网卡。N3 是基站连接核心网用户面的一侧。上行用“请求出现在 N3 的时刻”减去“请求出现在 TUN 的时刻”，同一 ping 请求按序号匹配。前三段来自同一宿主的抓包时钟，逐笔相加得到 TUN 侧往返。最右列是 ping 程序自身的计时，边界略有差异。

**三 UE 同一轮里，UE 3 比前两台的平均 RTT 多 4.921 ms，其中约 4.895 ms 对应上行请求段的差距。** 核心网侧往返和下行回复三台都接近。与双 UE 短测相比，前两台的 RTT 分别增加约 0.53、0.58 ms，同时涉及上行和下行。三 UE 组里第三台额外偏慢则主要集中在上行。

空闲探测后置会先保障基站已经知道的发送需求。如果一个新包刚到终端，基站尚未收到请求或掌握待发量，它能否赶上主动授权，仍取决于这一轮有没有剩余资源以及按什么顺序发探测。**这是需要检查的一条线索。** 这轮短测的基站调度观测关闭，TUN 到 N3 包含等待、传输和处理，所以目前只能定位到这段。要继续区分，应核对慢包的调度请求（SR）、授权、首次发送和重传时刻，再看偏慢是否随终端接入顺序移动。若证据指向探测分配顺序，再对照轮转方案。

抓包依据为双 UE 短测 TEST612 与三 UE 短测 TEST623。N3 路径见本地 TS 38.300 V19.4.0 §4.3.1.1，授权与发送请求见 TS 38.321 V19.4.0 §5.4.1、§5.4.4、§5.4.5。按包匹配和测量边界参考 P01《Dissecting 5G New Radio Latency》§III–IV、本地 PDF 第 2–4 页。

## 结果适用范围

两批均为同一宿主机的 RFsim 试验，沿用 66 PRB、0.625 ms TDD、原核心网和相同的三个软件 UE。较早的接入诊断里，基站调度记录的缓冲区在后段写满，丢弃了 201,657 条观测记录，当时的三个业务地址、路由和 60 个 ping 回复已独立核实。200 次短测关闭了调度观测器，对照的逐包时延来自业务端点和抓包。此前第二步正式表仍对应原调度顺序。

依据：TS 38.321 V19.4.0 §5.1.5、§5.4.1、§5.4.4 和 §5.4.5 用于区分随机接入竞争解决、授权、SR 和 BSR。TS 38.211 V19.5.0 §4.3.2、§7.3.2.2 用于解释时隙及 CCE/REG。名额计算、门限 0 的空闲资格和纯空闲探测处理顺序来自本项目 `gNB_scheduler_ulsch.c`。实验命令、计数及证据边界见 CHG467／TEST622。
