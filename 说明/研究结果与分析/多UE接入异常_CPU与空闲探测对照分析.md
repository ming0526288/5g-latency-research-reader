# 多 UE 接入异常：CPU 与空闲探测对照分析

我在建立第二步多 UE 基线时发现：第一步可运行的积极探测配置，并不能直接当作三 UE 的稳定工作点。目前已证实分核没有消除本次接入异常；减少空探测后，三个 UE 可以接入和完成短业务。完整根因链还未逐事件闭合。

本页保存最初的 CPU 分核和门限对照。后续逐轮记录，以及保留门限 0 时的新接入试验，见[门限 0 下第三个 UE 为什么接不进来](门限0下第三个UE的接入验证.md)。

## 我遇到了什么问题

共同条件为同一套现在代码、单宿主 RFsim、原核心网、n261、27.54756 GHz、120 kHz、66 PRB、0.625 ms TDD、PF、私有 HOL 关闭、MCS 上限 9、sync1。gNB 和各 UE 分终端直接启动，未加连续供样、额外线程池或启动相位控制。每个 UE 使用独立网络空间和已有订阅，未修改核心网数据库。

|运行条件|实际推进到哪里|业务结果|
|---|---|---|
|1 UE，门限 0|接入、TUN、路由通过|UDP 200/200 完整，均值 0.944 ms；20 包 ping 连通检查均值 0.873 ms|
|2 UE，门限 0|两个 UE 都接入|各 200/200 UDP 完整，均值 1.767 / 1.759 ms|
|第 3 个 UE 加入，门限 0|同步、SIB1、随机接入后反复重接入和 RRC 重配置|第三个 UE 未完成用户面接入；没有三 UE 业务 RTT|
|交换订阅接入顺序，门限 0|原先失败的订阅先接入时成功；换另一个订阅第三个接入仍失败|原失败订阅单独先接入，20/20 ping、均值 0.832 ms；三 UE 业务未开始|

这些是短测和诊断记录，不能代替正式多轮基线，也不能证明本机最多只支持两个 UE。

## 这次与原来的 D 槽启动问题不同

|现象|原来的采样启动停滞|本次第三个 UE 异常|
|---|---|---|
|最后推进位置|TCP 连接后，采样读取不继续，尚未进入正常同步接入|已经同步、读到 SIB1 并执行随机接入|
|后续表现|两端等采样|反复重接入、重配置、Msg4 负载增长|
|直接失败|采样推进停滞|gNB 的 Msg4 分配断言退出|

本次没有证据把故障归为“手动命令启动得不巧”。也不能把旧 D 槽等待解释直接套到这里。

## CPU 共核与分核：我怎样对照

本机有 24 个在线逻辑 CPU，所选 CPU 4、8、12 对应不同物理核。实际读取发现每个独立 UE 进程的 `UEthread_0` 默认均绑到 CPU 4。

我保持 gNB、两个 UE、门限 0、无线参数和业务不变，仅移动第二个 UE 的现有关键线程，按“分核→共核→分核→共核”重复。每轮每 UE 1200 个 56 B UDP 请求，前 100 个预热，目标 50 包/秒；分核为 CPU 4/8，共核为 CPU 4/4。没有改变线程池或调度算法。

|顺序|关键线程位置|UE 1 / UE 2 平均 RTT，ms|UE 1 / UE 2 P99，ms|完整请求数|
|---|---|---|---|---|
|1|分核 4/8|1.786 / 1.796|4.401 / 4.427|2400/2400|
|2|共核 4/4|1.768 / 1.773|2.727 / 2.703|2400/2400|
|3|分核 4/8|1.742 / 1.751|2.452 / 2.463|2400/2400|
|4|共核 4/4|1.796 / 1.742|2.473 / 2.450|2400/2400|

分核没有呈现稳定的 RTT 或 P99 改善。随后把三个 UE 的关键线程分别放到 CPU 4/8/12，第三个 UE 仍反复重接入，最终同样在 Msg4 分配处退出。因此，共用 CPU 4 不是本次失败的充分解释。这不等于排除了全部主机、线程池或高负载下的 CPU 瓶颈。

我记录了每秒 CPU 时间、绑核和调度计数。系统 `sched_schedstats=0`，不能把采到的运行队列等待计数当作完整、精确的排队证据。晚一次尝试减少活动 UE 时，gNB 实际已经退出，该操作不能作为“减少 UE 即恢复”的有效对照。

## 空闲探测门限是什么

基站当前认为 UE 没有待发数据时，仍可能主动给它一次小授权，让它有机会发新数据或报告缓冲区。没有数据时，这次安排会产生空开销。

|值|本实现资格门限的换算|含义|
|---|---|---|
|0|5 个时隙，即本配置 1 个 TDD 周期 0.625 ms|更积极地考虑空队列探测|
|1|80 个时隙，即 1 个无线帧 10 ms|降低空闲探测积极程度|

门限是调度资格条件之一，不是每个包固定等待的时间，也不是严格周期发送器。SR、基站已知积压、实际 TDD 机会、控制资源和调度名额都会影响是否真的发出授权。它不是 SR 周期、配置授权或预测算法。

## 代码为什么提示要检查调度资源

实际源码的上行预处理器采用以下工程估算：

$$N_{\mathrm{quota}}=\left\lfloor\frac{66}{4\times6}\right\rfloor=2.$$

其中 66 是本工作点 PRB 数；4 是代码写死的平均聚合等级估计；6 对应代码的每 CCE REG 数。这是实现名额估算，不是 3GPP 规定只支持两个 UE，也不是本小区真实 CCE 容量的完整计算。

`pf_ul` 按 UE 列表处理：空队列探测分配成功也扣减名额，且发生在后续已知数据候选的评分分配之前。日志确实出现过无空闲 CCE 的上行授权告警。这些共同提示探测、名额与控制资源可能相互挤占；本轮尚未启用逐事件观察器，不能把每个第三 UE 失败都直接算成同一种名额拒绝。

可以通俗地理解为争抢窗口，暂不能说无线信号已经发生了物理碰撞。PRACH 同前导碰撞、控制资源不足、调度未获服务、CPU 争用是不同机制，不能混称“撞车”。

## 单独减少空探测后发生了什么

我只把 `ulsch_max_frame_inactivity` 从 0 改为 1；其余配置文本保持一致，三个 UE 的关键线程恢复默认共用 CPU 4。没有修改 C 代码。

三个 UE 均完成接入；本轮实际 NAS 消息逐身份核对为 5QI 9、QFI 9，TUN 和 UPF 反向路由通过。56 B UDP 短测各 200 个请求全部回复，共 600/600；前 20 个预热后：

|UE|平均 RTT / ms|P99 / ms|
|---|---:|---:|
|1|6.477|11.361|
|2|6.494|11.387|
|3|6.848|12.405|

保持共核也能接入，与分核仍失败形成对照，说明授权探测设置是重要影响项。已在两批门限1直接启动中完成三UE接入，第一批另完成15次正式UDP，第二批完成ping先导；仍不能声称所有启动和负载都已经稳定，也不能把调大门限当成算法降时延收益。

## 为什么少探测，包反而可能更慢

积极探测消耗资源，也可能让新包较快赶上已有的发送机会。减少探测后，如果基站还不知道 UE 来了数据，就可能增加“等 SR 机会→请求资源→等授权→等目标 UL 时隙”的等待。

因此必须同时看业务时延和空授权代价。前面的约 1.8 ms 来自双 UE，约 6.5–6.8 ms 来自三 UE，不能把全部差值解释为门限效果。第二步已完成相同门限的1、2、3 UE共15次正式UDP与ping初步对照，详细数值在各项结果页。第一步门限 0 的 ping/UDP 双基线保留，不能改标签冒充门限 1 的结果。

## 已知结论与尚未完成的核验

|当前可以说|当前不能说|
|---|---|
|门限 0 在本轮三次第三 UE 接入尝试中出现异常|本机硬件只支持 2 UE|
|两种订阅顺序均失败；分核仍失败|所有 CPU 因素都已排除|
|改为门限 1，共核三 UE 接入并完成短业务|完整根因已逐事件证明、根本缺陷已修复|
|Msg4 负载增长后，分配断言直接导致 gNB 退出|标准要求崩溃，或任意异常都应增大门限|

下一步继续补共同设置的 ping/UDP 多 UE 基线，再用被动事件记录量化候选 UE、名额拒绝、CCE 拒绝和实际授权，不先改排序算法。还需负载扫描、空授权占用与长时稳定性，当前不宣布第二步全部完成。
