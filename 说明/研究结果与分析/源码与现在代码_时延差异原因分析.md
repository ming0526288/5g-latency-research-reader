# 原始源码与现在代码：时延差异原因分析

[结果与分析总目录](研究结果与分析总目录.md) · [第一步实验 1 的完整结果](第一步/1_源码与当前代码.md) · [分终端启动命令](../启动命令/第一步/1_源码与当前代码.md) · [相关知识点与完整源码差异](../算法知识点说明/十二步知识点/第一步/1_源码与当前代码.md)

## 这次找到的主要影响项

**同一套现在代码，只缩短空闲时的主动授权门限，平均 ping RTT 从 2.358 ms 降到 0.829 ms；切回默认门限后又回到 2.191 ms。** 原始代码另一次默认 ping 均值为 0.834 ms。这说明我可以保留必要修复，同时在本机单 UE、低负载条件下恢复约 0.8 ms 的水平。

造成这次额外等待的主要配置因素是**空闲时多积极地提供上行发送机会**，不是把 120 kHz 改小了，也不是必须加连续供样。下面的同程序对照支持这个判断；各层具体消耗多少毫秒，还没有逐包内部探针证明。

## 这是否说明提前授权有好处

**可以支持“更积极地提供上行授权机会，能够降低本场景时延”，不能推广成“只要提前授权，任何情况下都一定更快”。** 本次直接测到的是总 RTT 下降；减少请求/授权等待是与实现相符的机制解释，尚未逐包测出各段减少了多少。

|方式|本次做到了什么|尚未证明什么|
|---|---|---|
|频繁主动授权|不预测来包时间，缩短空闲探测门限，更频繁地安排上行机会；本机单 UE ping 下降|没有证明每个包的授权一定早于到达，也没有完成包级 SR/DCI 分解|
|预测式提前授权|预期应根据来包规律，在合适的时刻安排发送机会|本次没有实现预测器，不能把当前结果写成预测算法已验证或已复现|

通俗理解：原来数据来了以后，可能还要等“申请窗口”；现在基站更经常把窗口安排好，来包更容易赶上。**赶得上 UE 准备发送数据的时间、且资源足够时，才可能少等。** 授权早到但数据没来、或来包错过对应发送机会，都不保证得到同样收益。

这组结果为后续研究提供了参照：积极提供机会可以达到较低时延，但开销较大。预测或业务状态感知方法需要进一步证明，能否用更少空授权，保持接近这个参照的时延；当前没有自动开展这些新算法实验。

## 我怎样控制变量确认

以下三轮都使用同一新程序、同一修正配置、原核心网、相同目标、默认 56 B ICMP 数据和默认目标间隔。每轮 `ping -c 60`，全部收到，不剔除预热；都是分交互终端直接启动，两端均没有 `--continuous-tx`、额外线程池或 Python RAN 启动器。

|实际顺序|唯一改变的授权参数|收到 / 发出|平均 RTT / ms|最小 / ms|最大 / ms|
|---|---|---:|---:|---:|---:|
|先测默认值|`ulsch_max_frame_inactivity=10`|60 / 60|2.358|1.394|3.273|
|缩短门限|同一参数设为 `0`|60 / 60|**0.829**|0.623|1.041|
|再切回默认值|去掉覆盖，恢复 `10`|60 / 60|2.191|1.403|3.222|

第二轮只在基站命令末尾增加该参数，UE 和 ping 命令逐项相同；第三轮恢复第一轮的完整命令。二进制、原配置和基础运行文件收尾核验未变，没有重新编译，也没有删除修复。

这是一组 **A→B→A 的初步反向验证**。相对于两次默认轮，短门限这一轮均值低约 62%～65%；该百分比只描述本组均值，不是对所有负载、UE 数或尾分位的收益保证。原代码的 348 包均值 0.834 ms 是另一个批次，不能声称两者分布已经统计等价，或 0.829 ms 比它显著更好。

## 把参数写入独立配置文件后也能复现

为了让我以后仍然只用简单命令，另建 `gnb1.sa.band261.fr2.66PRB.5slot.low-latency.conf`，相对默认对照配置只增加 `ulsch_max_frame_inactivity=0`。基站命令只换配置文件，不再添加门限覆盖参数；其余程序和 UE 命令不变。

文件方式另测 **60/60 个回复，平均 RTT 0.843 ms，最小 0.654 ms、最大 1.274 ms**。这是配置文件交付确认，单独保存，不与三轮 A/B/A 混池，也不拿两次低时延运行声称所有条件都能达标。实际命令可直接从[启动命令页](../启动命令/第一步/1_源码与当前代码.md)复制。

## 原始代码为什么容易得到较小的 ping

原 `gNB_scheduler_ulsch.c::pf_ul` 有这段逻辑：对遍历到的第一个 UE，强制设置 `do_sched=true`。即使基站此时认为没有新数据、也没有收到 SR，这个 UE 仍可以进入最小上行授权分支。随后还要满足资源、控制信道和其他检查，并不是无条件保证发包。

现在代码取消了按列表位置给第一个 UE 的例外，所有 UE 采用共同资格条件：基站估计有待发数据、收到 SR，或者达到空闲探测门限之一成立时，才进入后续分配。在只有一个 UE、包间隔约 1 秒的小包业务中，基站经常先看到“队列为空”，因而这项改变会影响首包到来时有没有合适授权。

|机制|对稀疏小包意味着什么|
|---|---|
|原代码首 UE 强制主动调度|来包前可能已经安排了发送机会，少等请求和授权|
|现在代码共同资格＋默认空闲门限|空闲时机会更稀，来包可能需要请求，或等下次主动机会|
|现在代码共同资格＋短门限|保留共同资格规则，增加空闲时主动机会，本轮 RTT 回到约 0.8 ms|

**取消首 UE 特例是建立多 UE 共同基线的工程选择，不是 3GPP 强制要求关闭主动授权。** 我不需要把整个新代码退回原版，也没有为此次恢复低时延重新加入“永远优待第一个 UE”的分支。

## 参数 0 实际是什么意思

这份 OAI 实现中，`0` 既不表示禁用授权，也不表示资格条件永远为真。源码根据配置选择门限槽数：

```math
q(I)=\begin{cases}I N_f,&I>0,\\N_P,&I=0,\end{cases}
\qquad N_f=80,\quad N_P=5,\quad T_{\rm slot}=0.125\ {\rm ms}.
```

因此，本工作点的源码门限为：

```math
q(10)T_{\rm slot}=100\ {\rm ms},\qquad
q(0)T_{\rm slot}=0.625\ {\rm ms}.
```

`I` 是软件的空闲帧参数；`N_f` 是一帧的槽数；`N_P` 是一个 TDD 周期的槽数。判定使用源码计算的槽差，并在 TDD 下使用指定的参考 UL 槽，而非为每个包精确测量等待时间。达到门限也只取得候选资格，仍要经过资源分配。

**不能据此说默认每个包都等 100 ms，也不能说短门限下 RTT 必为 0.625 ms。** 有数据或 SR 会使 UE 更早进入候选，TDD、K2、主机处理和下行回复仍会影响总 RTT。本轮测的是往返总量，没有把约 1.4～1.5 ms 的均值差全部标成某一段实测 SR 时间。

## 为什么没有改频率，时延仍会改变

27.54756 GHz、n261、120 kHz、66 PRB、0.625 ms 周期和 3D＋混合槽＋1U 都保持不变。相同无线时间网格下，**安排发送机会的时机仍然可以不同**，所以相同 SCS 不保证相同端到端 RTT。

新配置保留 SDAP、SSB bitmap 和 SIB1 TDA 的既有修正；它们在这三轮中固定。因此，本次没有通过撤销 SDAP、QFI、封装、预算指针或同步修复来换取低时延。原/现版本所有改动各自贡献多少，尚未逐项拆开；本页确认的是同一新程序内该授权参数的影响。

## 低时延付出了什么代价

短门限更频繁地安排主动发送机会。若数据尚未到来，可能发送填充、控制内容，或者消耗未承载有效业务的资源；它不是免费降低时延。

终端最近几条 MAC 日志中，默认轮上行速率约 **18 kbps**，短门限轮约 **2968～2970 kbps**。这不是 56 B ping 的有效吞吐：MAC 统计会计入填充等内容，且这些日志没有对齐成精确业务窗口，不能据此计算精确资源占用百分比。它们与主动发送明显增多相符，完整资源代价仍需另测。

因此，这个配置适合作为**本机单 UE 低负载的低时延参照**。不能直接推广为多 UE 的最终策略；多 UE 下还要检查空授权是否占用其他 UE 的 PRB、CCE 或发送机会。后续真正要优化的是：接近原来的低时延，同时把空授权开销限制住。

## 启动失败和业务时延为什么分开记录

本次授权验证期间还保留了两次“TCP 已连接、但 UE 尚未进入同步”的启动失败，业务均未开始，RTT 为空。它们不计入三轮成功 ping，不填 0，也不当成很大的业务时延。没有采集这些失败的实际相位，不能直接认定又命中了旧 D 槽触发。

分终端运行能成功，不代表所有自然启动一定成功；短门限降低本轮业务 RTT，也不表示已经修好 RFsim 启动问题。启动过程的已有控制试验另见[启动失败原因与排查过程](原始程序启动失败_原因定位与控制变量全过程.md)。

## 依据、结果范围与下一步

- **协议要求：** TS 38.321 V19.4.0 §5.4.1 要求 UL-SCH 发送有授权；§5.4.4/§5.4.5 说明 SR/BSR。TS 38.300 V19.4.0 §10.3 描述动态上行分配。它们不要求每个应用包都先独立发送 SR，也没有替本 fork 指定 `10` 或 `0`。
- **实现与工程选择：** 原/现在代码 `gNB_scheduler_ulsch.c::pf_ul`、`nr_UE_is_to_be_scheduled`；`MACRLC_nr_paramdef.h` 的默认值；实际 A/B/A argv 和日志。这里仍通过 PDCCH 发动态授权，不是实现了配置授权 Type 1/2，也不是 AUGUSTE 预测算法。
- **时间网格与修正配置：** TS 38.211 V19.5.0 §4.3.1/§4.3.2；38.213 V19.5.0 §11.1/§13；38.214 V19.5.0 表 5.1.2.1.1-2；38.331 V19.4.0 §6.3.2 SDAP-Config；37.324 V19.0.0 §5.2.1 NOTE 2。取用户提供且已读本地版本，不声称官网最高版或全面标准认证。
- **测量方法背景：** P01《Dissecting 5G New-Radio Latency》，IFIP Networking 2025 本地 PDF 第 2～3 页、§III；指定《5G移动通信系统设计与标准详解》第 2 章、本地 PDF 第 49～55 页及调度/SR/BSR背景 PDF 第 530～539 页沿既有已读定位。它们支持区分路径与等待，不为本机 RTT 数值或参数效果背书。

本页是单 UE、单工作点的 ICMP RTT 对照；没有新的 UDP 单向测量、层内分解、机械臂执行闭环或 P99/P99.9 保证。程序运行和网页维护的工程步骤不适用额外 3GPP 数值规定。
