# 100 到 200 MHz 单 UE 降低时延方案二（配置授权 CG）

**门限 0 和配置授权都可能让 UE 少等一次调度请求。区别在于 UE 怎么知道哪次可以发。** 门限 0 时，基站可以在还没收到调度请求时主动发一份动态授权。配置授权（Configured Grant，CG）是先给 UE 配好可周期复用的资源，之后 UE 按生效的配置在合适的机会发送。

## 同样是提前给机会，区别在哪里

|对照项|本项目的门限 0|3GPP 配置授权 CG|
|---|---|---|
|决定了什么|决定空闲 UE 何时具备候选资格，基站每次仍要决定给谁、给多少资源。|提前配置周期、时频资源等，UE 保存生效的授权。|
|UE 怎么知道何时能发|基站通过下行控制信道发送一份动态授权，告诉 UE 这次在哪个上行时隙、用哪些资源发。|UE 按已经生效的周期配置找到下一次发送机会，每次机会可直接按配置使用。|
|数据来了是否一定要先发 SR|已经有合适的动态授权时，对应包可以直接用它。基站也可以在收到 SR 前主动给授权。|满足使用条件并赶上已配置的机会时，数据可直接发送，省去对应包的临时请求和动态授权等待。|
|没有数据时的代价|基站可能照样发授权并分配资源，有些授权没有带业务数据。|周期资源如果为该业务预留，业务没来时可能闲置。周期和业务相位匹配能减少等待。|
|本项目的实现状态|本项目已经运行，`ulsch_max_frame_inactivity = 0` 用在基站调度资格判断。|独立研究副本已在 200 MHz 单 UE RFsim 中跑通 Type 1 和 Type 2。|

**CG 有两种启用方式。** Type 1 由 RRC 直接配置上行授权。Type 2 先由 RRC 配置，然后通过 PDCCH 上的控制信令激活或停用，激活后授权按配置重复使用。Type 2 的激活信令和门限 0 的逐次动态授权是不同操作。这里的 SR 是 UE 向基站申请上行资源的调度请求，PDCCH 是基站发送控制信息的下行信道。[3GPP TS 38.331](https://portal.3gpp.org/desktopmodules/Specifications/SpecificationDetails.aspx?specificationId=3197) · [3GPP TS 38.321](https://portal.3gpp.org/desktopmodules/Specifications/SpecificationDetails.aspx?specificationId=3194)

| CG 类型 | 怎么启用 | 适合验证什么 |
| --- | --- | --- |
| **Type 1** | 基站通过 RRC 直接配置周期性的上行发送机会，配置生效后 UE 就能在符合条件时使用。 | 业务周期稳定时，提前配置发送机会能减少多少上行等待。 |
| **Type 2** | 基站先用 RRC 配置，再用下行控制信息（DCI）激活这些周期性的发送机会，也可以通过 DCI 停用。 | 业务有明显的开始和停止阶段时，按需启停能否减少空闲资源占用，以及从激活到首次发送要等多久。 |

## 用一个待发的小包来理解

**门限 0 的例子。** 基站判断 UE 空闲到了候选门限，还有可用资源，就主动发消息安排「接下来这个上行时隙可以发」。若小包及时进入待发队列，就能用这份授权。下次发送仍由新的动态授权决定。

**CG 的例子。** 假设配置生效后，每 2.5 ms 有一次可用上行机会，依次是 2.5、5.0、7.5 ms。包在 2.4 ms 已准备好且赶得上，则等 0.1 ms。包在 2.6 ms 才准备好，则要等到 5.0 ms，也就是 2.4 ms。等的时间就是「下一次可用机会的时刻 − 包准备好的时刻」。这是说明相位影响的算例，省略了本机处理时间，数字来自示意设置。

## 这对 100 MHz 和 200 MHz 对照意味着什么

门限 0 的「0」是软件参数值。在本项目 TDD 配置下，代码把空闲资格门限换算成一个 TDD 周期，即 5 槽 × 0.125 ms = 0.625 ms。符合资格后，基站还要检查实际资源才能发授权。[第二步知识点](../算法知识点说明/十二步知识点/第二步知识点.md)

已测的单 UE 对照，两档都是每隔 5 槽**准备**一次动态上行授权。100 MHz 主机上平均间隔 0.222 ms，200 MHz 是 0.453 ms。配置授权可以改变特定业务等授权的方式，当前测试看到的 RFsim 样本推进速度属于另一个环节。现有结果也没有逐包关联 UE 收到授权和实际发出该包的时刻。[100 到 200 MHz 的时延变化](100到200MHz单UE时延变化的原因.md)

## Type 1 首轮 200 MHz 单 UE ping 对照

**这轮 Type 1 跑通，平均 RTT 和 P99 都高于前后两轮门限 0。** 我用同一套 gNB 和 UE 程序、同一份 200 MHz 配置依次跑「门限 0 → Type 1 → 门限 0」。每轮一个 UE，n261、120 kHz、132 PRB，发 200 个 56 B ICMP 数据区的 ping，目标间隔 20 ms。前 20 个为预热，表中 RTT 用后 180 个计算。

| 轮次 | 发出／收到 | 平均 RTT / ms | P99 RTT / ms |
| --- | ---: | ---: | ---: |
| 历史门限 0（TEST-633） | 200／200 | 1.354 | 1.951 |
| 门限 0，第 1 轮 | 200／200 | 1.302 | 1.855 |
| **CG Type 1** | **200／200** | **1.420** | **2.088** |
| 门限 0，切回轮 | 200／200 | 1.349 | 1.884 |

gNB 下发了 `ConfiguredGrantConfig`，UE 日志确认应用在上行 BWP 0。Type 1 每 5 槽安排一次发送机会，即 0.625 ms 无线时间。每次在完整上行槽中放 5 PRB，MCS 为 9，有待发数据才安排 PUSCH。这个固定配置用于本次先导。

相比两轮新门限 0 的平均值，Type 1 的平均 RTT 增加 **0.095 ms**。逐包关联同机 TUN 和 N3 抓包后，TUN 往返均值增加 0.095 ms，其中请求上行段增加 0.086 ms、核心网侧减少 0.010 ms、下行段增加 0.019 ms。当前可定位到请求上行段。段内的排队、配置机会和主机处理时间仍需逐包拆分。

这是一轮 Type 1、两轮门限 0 的 RFsim 短测。适用范围是单 UE 和当前低负载，使用固定单层上行配置。资源空闲比例、CG HARQ 重传与真实射频待验证。[代码目录](../研究代码/代码目录.md)

## Type 2 激活后的 200 MHz 单 UE ping 实测

**Type 2 已在 RFsim 中通过 PDCCH 的 DCI 激活，并完成 MAC 确认。这轮激活后的平均 RTT 为 1.409 ms，P99 为 1.982 ms。** 我在同一构建依次测 Type 2、门限 0、Type 1。三组保持 n261、120 kHz、132 PRB、同一核心网与 TDD、每轮 200 个 56 B ping、目标间隔 20 ms。各组用后 180 个样本统计。两种 CG 均用 5 槽周期、完整 UL 槽、5 PRB 和 MCS 9。

| 模式 | 发出／收到 | 平均 RTT / ms | P99 RTT / ms | 平均请求上行 TUN→N3 / ms |
| --- | ---: | ---: | ---: | ---: |
| 门限 0 | 200／200 | 1.259 | 1.536 | 0.684 |
| CG Type 1 | 200／200 | 1.340 | 1.642 | 0.745 |
| **CG Type 2** | **200／200** | **1.409** | **1.982** | **0.797** |

Type 2 比本次门限 0 的平均 RTT 高 **0.150 ms**，比同构建 Type 1 高 **0.069 ms**。相对于门限 0，抓包中的请求上行段增加 **0.114 ms**，是当前差异最大的分段。每种模式仅一轮，尚无法判断该差值在重复运行中是否稳定。

gNB 在 655.35 槽发出 DCI 0_1，UE 验证后在 655.39 槽发出确认，gNB 在该槽收到。4 槽是 **0.500 ms 的无线时间**。实际 ping 在收到确认后才开始，表中 RTT 测的是已激活后的通信往返。还需要另测应用首包触发激活的等待、停用后的空闲资源消耗和 CG 重传。激活校验与确认的依据为 TS 38.213 V19.5.0 §10.2 表 10.2-1，以及 TS 38.321 V19.4.0 §5.4.1、§5.8.2、§6.1.3.7。实测与前一次失败详情见 CHG-489、TEST-644。

AUGUSTE 也能在 SR 之前安排资源，它使用业务到达预测来决定何时发动态授权。[AUGUSTE 原文](https://arxiv.org/abs/2606.03664v1)

依据为本地 TS 38.331 V19.4.0 §6.3.2 的 `ConfiguredGrantConfig`，TS 38.306 V19.4.0 的 `configuredUL-GrantType1`，TS 38.321 V19.4.0 §5.4.1、§5.4.4、§5.8.2，TS 38.214 V19.5.0 §6.1.2.3，以及 TS 38.211 V19.5.0 §4.3.2 表 4.3.2-1。实现、启动命令和核验见 CHG-488、TEST-643。[3GPP TS 38.214](https://portal.3gpp.org/desktopmodules/Specifications/SpecificationDetails.aspx?specificationId=3216)
