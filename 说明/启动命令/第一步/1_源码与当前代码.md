## 我原先使用的启动命令

下面保留我提供的原命令，作为后续复测的参照。**这次已直接用原程序、原配置和原核心网测通。** 由于当前主机没有 `192.168.10.1`，本次单机 UE 实际使用 `127.0.0.1`；原命令仍在下面保留，不能声称当前网络完全等同历史部署。

先启动核心网：

```bash
cd ~/oiwireless/oiwireless-5gc-deploy
./run-5gc.sh
```

启动基站：

```bash
cd ~/oiwireless/oi-wireless-ran/cmake_targets/ran_build/build
sudo ./nr-softmodem -O ../../../targets/PROJECTS/GENERIC-NR-5GC/CONF/gnb1.sa.band261.fr2.66PRB.5slot.dpdk.conf --sa --rfsim --rfsimulator.serveraddr server
```

新开终端，进入同一构建目录后启动 UE：

```bash
cd ~/oiwireless/oi-wireless-ran/cmake_targets/ran_build/build
sudo ./nr-uesoftmodem --band 261 -C 27547560000 -r 66 --numerology 3 --ssb 301 --sa -O ../../../targets/PROJECTS/GENERIC-NR-5GC/CONF/ue.oiwireless.conf --ue-txgain 0 --ue-rxgain 20 --ue-fo-compensation --rfsim --rfsimulator.serveraddr 192.168.10.1
```

UE 完成接入、用户面可用后，新开终端启动业务：

```bash
ping 172.11.200.25 -I oaitun_ue1
```

这里的 `192.168.10.1` 是原命令中的 RFsim 服务端地址，`172.11.200.25` 是原 ping 目标。两者用途不同，不能为了让命令看起来一致就相互替换；实际可达性仍待恢复测试时确认。

核心网直接执行上面的原 `run-5gc.sh`，没有使用研究核心副本或 SMF 修复。实际直接读取原二进制/配置，进程工作目录与日志单独保存，以免统计文件写回原目录；原模块加载路径在现场已核。

```bash
cd /home/lbh/oiwireless/oi-wireless-ran-latency-analysis
sudo -n /usr/bin/python3 -B research/latency-analysis/original-native-ping-v1/environment.py --output /home/lbh/oiwireless/analysis-source-audit/original-native-ping-20261113/attempt-01/environment-before.json
sudo -n /usr/bin/python3 -B research/latency-analysis/original-native-ping-v1/run.py --output /home/lbh/oiwireless/analysis-source-audit/original-native-ping-20261113/attempt-01
```

以上是已发生的失败轮，证据目录不能覆盖重跑。之后另外创建 `attempt-02`，同一运行器加 `--gnb-continuous-tx`，只给 gNB 加已有 `--continuous-tx`；完成业务后，又创建 `attempt-03` 去掉该选项。后两轮均成功，不能把有选项成功写成必需条件。

```bash
sudo -n /usr/bin/python3 -B research/latency-analysis/original-native-ping-v1/run.py --output /home/lbh/oiwireless/analysis-source-audit/original-native-ping-20261113/attempt-02 --gnb-continuous-tx
sudo -n /usr/bin/python3 -B research/latency-analysis/original-native-ping-v1/run.py --output /home/lbh/oiwireless/analysis-source-audit/original-native-ping-20261113/attempt-03

python3 -B research/latency-analysis/original-native-ping-v1/analyze.py --output /home/lbh/oiwireless/analysis-source-audit/original-native-ping-20261113/attempt-03
```

每个新根都先核协议和环境，不是只替换目录就可跳过准备。运行器会启动真实 RAN/抓包和业务，不是只读分析脚本；已有根禁止重复执行。

两次成功轮的业务命令都是：

```bash
ping -D -n -I oaitun_ue1 -c 60 -W 2 172.11.200.25
ping -D -n -I oaitun_ue1 -c 2200 -W 2 -i 0.02 172.11.200.25
```

第二条每轮执行 3 次，分别保存；数据默认 56 B。第一组去掉前 5 包，后三组各去掉前 200 包作为预热。实际间隔从抓包统计，约 1.024 s 和 25 ms，不能只看命令参数。

本次三次 RAN 和抓包均已回收，TUN 已消失；原核心网保持运行。新增失败栈、原文件保护、来源和完整结果见 CHG410/TEST560 及本项结果页。早期 `original-ping-v2` 的启动中断仍是历史事实，不改写为本轮已执行。

实际正式批次在同一版控制方法下执行，核心网不重启、不换版本。第一批两种实际握手位置各 4 次，交错顺序；第二批固定第 1 个 D 槽末，仅开连续供样，4 次。新目录不可覆盖重跑。

```bash

sudo -n /usr/bin/python3 -B research/latency-analysis/original-startup-control-v1/run_batch.py --output /home/lbh/oiwireless/analysis-source-audit/original-startup-control-20261113/phase-main-03 --mode phase

```

这是带调试暂停/放行的启动诊断，保留原程序、原配置、原核心网；不将其中 5 包 ping 作为时延优化统计。`phase_gate.py` 核对所有线程暂停后的真实采样位置，再在原握手写入点复核，未命中不算有效样本。旧控制未命中及一次误启动的旧方法复跑都保留，详 TEST565。

本机普通 RFsim 仿真可按已验证的规避方式给 gNB 原命令增加 `--continuous-tx`；UE 仍按原无线参数，单机连接 `127.0.0.1`。此选项为 OAI 软件供样行为，3GPP 没有要求必须使用。它在已测试的 D 槽末启动对照中规避了等待，不能保证所有图样/多 UE/射频场景，也不能当作业务尾时延算法收益。
