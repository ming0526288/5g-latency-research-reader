## 56 B ping 与 16 B ping：里面的计时部分相同，总长不同

本机 iputils ping 的计时字段占 16 B。它装在数据区里面，不是数据区之外再加一个 16 B 头。

```text
56 B ping 数据区 = 16 B 计时信息 + 40 B 填充
16 B ping 数据区 = 16 B 计时信息 +  0 B 填充
```

|说法|命令|数据区总长|其中计时信息|其余填充|普通内层 IPv4 包长|
|---|---|---:|---:|---:|---:|
|原命令默认 ping|不写 `-s`，或 `-s 56`|56 B|16 B|40 B|84 B|
|新增的小包对照|`-s 16`|16 B|16 B|0 B|44 B|

二者都能测 RTT，主要区别是发送数据区多了或少了 40 B 填充。这里“数据”也包括测量用的时间信息和填充，不表示全是工业业务内容。两者数据区之外都另有 8 B ICMP 头与无选项 IPv4 20 B 头。

第 1 项固定 **56 B 数据区 ping**，比较最开始／现在 OAI 代码；第 2 项才取 **16 B 数据区 ping 与 16 B 数据区 UDP**。你最初不带 `-s` 的命令是 56 B；后来为了包长分析，才增加 16／256／1200 B。原始 0.834 ms 与现在 0.829 ms 都是 56 B 的不同批次，16 B ping 本轮为 0.832 ms，不能合并或作为严格版本收益。

UDP 的“16 B 测量字段”另有所指：它是本项目放在 UDP 数据区里的格式标记。本项 UDP 数据区总长恰好也为 16 B；第 3 项则将该标记放进 256 B 数据区。它与 ping 的计时字段不是同一种格式。

依据：[iputils 20211215 `ping.c` 的计时判据和写入函数](https://github.com/iputils/iputils/blob/20211215/ping/ping.c#L851)：数据区至少容纳 `struct timeval` 时启用计时，`ping4_send_probe` 将其写入 ICMP 数据区；本机 ELF 为 64 位、C ABI 的 `struct timeval` 为 16 B。该 16 B 限定本机工具／ABI，不推广所有系统或 ping 版本。算术是 56=16+40、84=56+8+20；3GPP 不规定 ping 的默认包长与本项目测量格式。

## 16 B 在本项指数据区总长

|项目|ping|UDP 请求—回复|
|---|---|---|
|工具设置|`ping -s 16`|`--size 16 --header-bytes 16`|
|数据区总长|16 B|16 B|
|数据区内装什么|ping 自己的计时/测试数据，具体布局依工具实现|项目 16 B 标记：版本、请求/回复类型、UE、轮次、序号等|
|数据区之外的头|8 B ICMP 头|8 B UDP 头|
|无选项 IPv4 头|20 B|20 B|
|本项内层 IP 包长|44 B|44 B|
|回复由谁处理|内核 ICMP 实现|本项目用户态 UDP 回复程序|

这里不再使用“16 B 测量字段装进 256 B 总数据区”的旧定义。那属于另一个长度条件，不能当作 16 B 数据包的测量。

## 同样大小，不代表处理路径相同

ping 测 ICMP 往返时间；UDP 应用 RTT 包含用户态唤醒、业务编码/校验、系统调用和回复准备等边界。两者数据区都为 16 B 时，可以比较这两种测试方式下的实测值，但不能把差值全部叫作无线差异，也不能用 ping RTT 除以二代替 UDP 单向时延。

UDP 精简头不携带四个应用时间戳；它们在发送端和回复端日志中记录，按 UE、轮次和序号关联。日志与时钟域满足条件时，仍能计算上行、回复区间、下行和总 RTT；PDCP/RLC/MAC/PHY 分层还需独立探针。测量格式的详细字段与四时刻定义见[第 3 项知识点](3_80B与16B的UDP.md)。
