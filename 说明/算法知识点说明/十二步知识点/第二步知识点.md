## 双 UE 和三 UE 用的什么方案

|实验组|上行算法与空闲探测设置|具体做法与已测情况|
|---|---|---|
|**门限 0 · 双 UE**|**PF（比例公平）＋原探测顺序**。空闲比较门槛为 5 槽，折算 **0.625 ms**，较容易获得主动探测资格。|两台软件终端分别接入同一个基站，再在重叠时段发包。原顺序下两台能测通，ping 和 UDP 都完成了每台三轮、共 6600 次的正式测量。|
|**门限 0 · 三 UE**|**PF ＋空闲探测后置**。仍用 5 槽门槛，改变的是基站什么时候处理纯空闲探测。|原顺序下，前两台的探测多次用完当轮名额，第三台虽发出请求却常轮不到，三台未能共同接入。试验方案把纯空闲探测放到已有请求或待发数据的处理之后。改后，三台逐一接入再同时开展业务，ping 和 UDP 分别完成每台 200 次短测。第三台时延仍偏高，正式三轮待测。|
|**门限 1 · 双 UE**|**PF ＋原探测顺序**。空闲比较门槛为 80 槽，折算 **10 ms**，较难获得主动探测资格。|只把基站配置里的门限由 0 改为 1。两台分别接入，再在重叠时段发包，ping 和 UDP 都完成了每台三轮、共 6600 次的正式测量。|
|**门限 1 · 三 UE**|**PF ＋原探测顺序**。沿用 80 槽门槛。|同一配置下依次接入三台，再让三路业务在同一时段跑。ping 和 UDP 都完成了每台三轮、共 6600 次的正式测量。|

### 名词解释

- **UE**是终端。双 UE 和三 UE 都共用一个核心网、一个基站。每台软件终端有独立的身份、进程和虚拟业务网卡。先逐台接入并确认网卡和路由，全部就绪后才发业务。
- **PF（比例公平）**。基站给已知有数据要发的终端排队时，会同时看一台终端这次大约能发多少、过去平均发了多少。在当前发送能力相近时，过去发得较少的终端可以得到更高的优先级。[PF 的详细例子](../调度算法入门/PF_知识点说明.md)
- **上行与授权**。上行是终端向基站发数据。授权是基站安排一次发送机会，告诉终端什么时候、用哪些无线资源发。
- **SR 与数据积压**。SR 是终端举手说“我需要发送机会”。BSR 是终端报告还有多少数据排队。基站收到 SR 或估计仍有数据待发，都可以按相应分支处理，空闲探测门槛只影响下面的主动尝试。
- **空闲探测**。基站暂时没收到待处理的请求，也没估计到还有数据排队，满足空闲条件后可以试着给终端一次小的发送机会。有新包赶得上时可以用掉这次机会。若没有业务数据，这次安排也会占用资源。
- **门限 0 与门限 1**。两者是同一个参数 `ulsch_max_frame_inactivity` 的取值。在本次 120 kHz 配置里，0 走按一个 TDD 周期计算的分支，门槛是 5 槽。1 按一个无线帧计算，门槛是 80 槽。单槽 0.125 ms，所以比较门槛分别折算成 0.625 ms 和 10 ms。达到门槛只获得主动探测资格，实际授权还取决于可用资源和调度。每个包的时延要单独测量。
- **原探测顺序与空闲探测后置**。原顺序下，基站按列表检查终端时，遇到满足空闲条件的终端就可能先给探测。后置则是先处理已收到的请求、已知待发数据和需要重传的数据，剩下的资源才安排纯空闲探测。门限 0 的资格判定和已知待发数据的 PF 评分继续使用原规则。进一步让终端轮流获得剩余探测机会，仍是待验证的候选方案。[三 UE 上行调度优化方案](../../研究结果与分析/三UE上行调度优化方案.md)
- **同时发包**指两路或三路业务在同一段时间运行，各台的发包时刻可以错开。ping 和 UDP 分开测试，请求数据区均为 56 B。

#### 为什么最后一台很少拿到提前授权

- **可以提前给。** 这里的“提前”指基站在收到调度请求（SR）前，先给终端安排一次上行发送机会。前两台就是这样拿到探测授权的。如果终端恰好有新包，而且赶得上这次发送，就可以少等一次请求。
- **不够的是当轮剩余的调度名额。** 三台都符合门限 0 的探测条件时，假设这一轮只剩两个名额。程序先检查排在前面的两台，分别给了探测授权，最后一台这轮就拿不到。反序实验确实观察到这种情况出现 1,123 轮。这个结果说的是当前程序的名额分配，总无线带宽是否不足还需要另外验证。

有新包的终端错过了主动授权，就可能要等下一次 SR 机会。后置策略会优先处理已经收到的请求，因此这批慢包主要等在发送 SR 之前。协议对授权和 SR 的定义见本地 TS 38.321 V19.4.0 §5.4.1、§5.4.4。名额及遍历顺序来自本项目的 `pf_ul` 和 TEST628 的实际记录。

#### 两个名额怎么算，能改成三个吗

**可以把每轮调度上限设成 3 做对照。** 第三个名额能否用上，还得看这一轮有没有地方发授权通知，以及目标上行时隙有没有资源供第三台发送。

当前代码先用下面的粗估式给本轮上行调度设置总上限。整数除法会舍掉小数部分。

```text
本轮总名额 = min(向下取整(66 ÷ (4 × 6)), 8) = 2
```

|数字或名词|在代码里是什么意思|
|---|---|
|66 PRB|这次配置的上行载波带宽输入。PRB 可理解为频率划分的一小块。|
|4 CCE|程序估算一条授权通知平均占用 4 个控制信道单元。真实聚合等级由基站按该 UE 的配置选择。|
|每 CCE 6 REG|协议规定的控制信道结构。一个 REG 占一个资源块和一个 OFDM 符号。|
|8|当前 FAPI 实现的 `MAX_DCI_CORESET` 上限，代码用它限制估算值。|

66 来自**上行载波带宽**，而 CCE 和 REG 属于**下行控制区域**。所以这个计算只是代码估算的调度上限。真正的授权通知位置要按控制区域（CORESET）、该 UE 允许监听的位置和当时的占用来检查。

**总名额和剩余探测名额要分开看。** 假设把总上限设成 3，这一轮已经给有数据的终端用掉 1 个，就最多剩 2 个用于探测。若 3 个都还空着，也要逐台检查授权通知能否放下，以及指定上行时隙有没有能用的连续 PRB。提高上限只是让程序有机会尝试给第三台分配。

如果要做 2 和 3 的单因素实验，可以把软件上限独立配置，保留真实控制和上行资源检查，记录第三台实际有没有拿到授权、空授权增加多少、各台时延怎么变化。3 可以作为调度名额，PDCCH 实际支持的聚合等级是 1、2、4、8、16 CCE。现在已有的正反序结果沿用上限 2。

代码位置是 `gNB_scheduler_ulsch.c` 的 `nr_fr1_ulsch_preprocessor`、`pf_ul` 和 `allocate_minimum_ul_probe`。协议依据为 TS 38.211 V19.5.0 §7.3.2.1 表 7.3.2.1-1、§7.3.2.2，以及 TS 38.213 V19.5.0 §10.1。

#### 调度名额和 PF 公平有什么关系

|问题|这套代码怎么处理|
|---|---|
|一轮最多发几份上行授权？|先算总名额，再在授权成功时扣减。这轮配置算出 2 个。|
|基站知道几台终端有数据排队时，先安排谁？|对进入待发数据候选的 UE，PF 用“这次估计能发的数据量 ÷ 过去的平均吞吐量”评分，优先尝试分配给分数高的 UE。授权仍要通过资源检查。|
|处理完实际需求，剩余探测给谁？|当前后置策略按列表顺序查看纯空闲探测候选。前两台用完余量时，排在后面的终端要等下一次发送机会。|

例如，两份名额都空着，三台都进入已知待发数据的候选队列时，PF 评分会影响谁先获得这两份名额。如果三台都只符合空闲探测条件，前两台仍可能按列表顺序拿走名额。**这轮测到的等待出在后一种分配。** 这些轮次里，基站既没收到最后一台的 SR，也没估计到它有积压，因此没有对它做待发数据的 PF 评分。收到 SR 后，基站会处理这份发送需求。把总上限加到 3 会多一次分配尝试，轮转则会改变剩余机会先给谁。

这三步来自本项目的 `nr_fr1_ulsch_preprocessor`、`pf_ul` 和 TEST628。TS 38.300 V19.4.0 §10.3 说明基站动态分配上行资源的机制。PF 的通俗解释和评分例子见[PF 知识点](../调度算法入门/PF_知识点说明.md)。

原顺序和后置策略的过程对照见 TEST622。双 UE 和三 UE 的正式结果来自 TEST621 及门限 1 UDP 已有正式记录，门限 0 后置短测来自 TEST623。门限 0 单 UE 的正式值复用第一步参照。

### 门限换算的代码口径

`gNB_scheduler_ulsch.c` 的 `nr_UE_is_to_be_scheduled` 用“基站估计有待发数据、收到 SR、内部空闲槽差达到门槛”三个条件判断资格，任一个成立即可。`pf_ul` 再按剩余资源和不同处理分支分配。TDD 分支用 `last_ul_frame` 和 `1 + nrofDownlinkSlots` 重建参考位置，再与目标上行帧槽比较。上表的毫秒值描述这个内部比较，授权节奏以实际记录为准。

协议依据为 TS 38.211 V19.5.0 §4.3.2 和 TS 38.331 V19.4.0 §6.3.2 的 `TDD-UL-DL-Pattern`，分别说明槽和 TDD 配置。TS 38.321 V19.4.0 §5.4.1、§5.4.2.2、§5.4.4、§5.4.5 分别说明上行授权、重传、SR 和 BSR。PF 评分、门限 0/1 及后置顺序来自本项目基站代码和实验配置。测量边界参考 P01《Dissecting 5G New-Radio Latency》§III–IV、本地 PDF 第 2–4 页，调度背景参考教材《5G 移动通信系统设计与标准详解》§13.1.1.2、本地 PDF 第 530–532 页。

## 先导 正式 新测和复用是什么意思

表里的词分成两类：“先导／正式”说明测量规模和用途；“新测／复用”说明数据来源。它们可以同时出现，例如“复用三轮正式数据”。这些词与门限值、工具和包长分别记录。

|表中用词|通俗含义|本项目对应做法|
|---|---|---|
|先导|先做一轮短测，检查多个终端能否通信并看初步时延|每 UE 发 200 个请求；成功组收到 200 个回复；前 20 个预热、后 180 个算时延|
|正式|按事先固定的样本数和轮次采集，观察均值与 P99 的轮间表现|每轮每 UE 发 2200 个请求，前 200 个预热、后 2000 个统计；同一条件做三轮|
|新测|该组数据在这一批实验中另外采集|门限 1 的单 UE ping 三轮是新采集的，没有沿用门限 0 的数值|
|复用|已经测过的同一组数据，在另一个页面再次引用|门限 0 的单 UE ping/UDP 引用第一步三轮数据，不再发包，也不增加样本数|

“先导各 200/200”表示每个 UE 各自发出 200、收到 200；“正式各 6600/6600”表示每个 UE 在三轮中累计发出 6600、收到 6600，即 3 × 2200。斜杠前后是发出数和收到数，单位是请求次数，不是 B。

|测量规模|每 UE 完整请求／回复|每 UE 用于时延统计|预热数量|
|---|---|---|---|
|一轮先导短测|200／200|180|20|
|一轮正式测量|2200／2200|2000|200|
|三轮正式测量合计|6600／6600|6000|600|

预热是运行前就约定的试跑部分，完整原始记录仍保留；不能事后为了让时延变小任意删包。两 UE 的“各 6600”合计是 13200 次完整事务，三 UE 合计是 19800 次；每个请求与对应回复算一笔事务，不能再乘二当作事务数。

例如“均值 1.709／1.707 ms”是 UE 1 与 UE 2 各自的平均时延，不是两轮，也不是两种负载。“6.327／6.330／6.477 ms”同样对应三个 UE，各自均值由其三轮统计样本计算。

## 重复 大包与大负载的区别

|工作|改变什么|本次是否属于这种工作|
|---|---|---|
|同条件分轮重复|相同包长、目标速率与配置下，另发一批请求|是，每轮 2200 次、前 200 次预热，每条件三轮|
|加大包长|例如数据区由 56 B 改为 256 B|否，本批始终 56 B|
|加大负载|例如保持 56 B，减小间隔，提高每秒包数|否，沿用每 UE 50 包／秒或全部 UE 合计 50 包／秒|

更长的观察不等于更大的每秒负载；三轮也不自动证明样本独立或 P99 稳定。分轮、实际间隔和慢包均保留。原生 ping 分终端自然发包，还要核对各 UE 的业务时段确实重叠；本次发现一轮无重叠后，单列保留并补同条件轮次，没有根据时延高低挑选数据。

计数与完成范围来自本项目实际实验及 TEST621。3GPP 没有规定本项目必须选择 200、2200、三轮或这些包长／业务速率；这是测量设计，新增协议公式不适用。

## 本轮所谓负载：目标每UE50包/秒

|配置|1 UE|2 UE|3 UE|
|---|---|---|---|
|每UE速率固定|50包/秒|各50包/秒，总100|各50包/秒，总150|
|总速率固定|总50包/秒|各25包/秒，总50|各约16.667包/秒，总50|

每个请求数据区56 B，等长回复另计。用十进制Mbps：

$$R_{\mathrm{UL,payload}}=N\times56\times8\times\lambda_{\mathrm{UE}}/10^6.$$

每UE50包/秒对应单UE上行请求数据区0.0224 Mbps；2/3UE总上行请求为0.0448/0.0672 Mbps。内层IPv4通常84 B，对应单UE0.0336 Mbps；不代表全部无线资源或CPU工作量。下行等长回复再按其包率计算，不能把上行单向值直接叫双向总负载。

这些包长与目标速率由本项目选择，不是OAI/3GPP默认工业流量。门限0/1只影响空闲探测资格，不等于业务速率0/1。不同工具目标间隔相同，实际发包节奏仍可能不同，结果JSON中保留实际TUN间隔。表里的1.709/1.707表示两个UE各自的时延，不是两种负载。

可将整个实验想成两套时钟：业务生成决定什么时候来包；无线调度决定什么时候给发送机会。减少空探测可能省控制资源、增加新包等待；是否有效必须同时看完成率、时延和资源开销，不能只看发包Mbps。
