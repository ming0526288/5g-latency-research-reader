## 先导 正式 新测和复用是什么意思

表里的词分成两类：“先导／正式”说明测量规模和用途；“新测／复用”说明数据来源。它们可以同时出现，例如“复用三轮正式数据”。这些词与门限值、工具和包长分别记录。

|表中用词|通俗含义|本项目对应做法|
|---|---|---|
|先导|先做一轮短测，检查多个终端能否通信并看初步时延|每 UE 发 200 个请求；成功组收到 200 个回复；前 20 个预热、后 180 个算时延|
|正式|按事先固定的样本数和轮次采集，观察均值与 P99 的轮间表现|每轮每 UE 发 2200 个请求，前 200 个预热、后 2000 个统计；同一条件做三轮|
|新测|该组数据在这一批实验中另外采集|门限 1 的单 UE ping 三轮是新采集的，没有沿用门限 0 的数值|
|复用|已经测过的同一组数据，在另一个页面再次引用|门限 0 的单 UE ping/UDP 引用第一步三轮数据，不再发包，也不增加样本数|

“先导各 200/200”表示每个 UE 各自发出 200、收到 200；“正式各 6600/6600”表示每个 UE 在三轮中累计发出 6600、收到 6600，即 3 × 2200。斜杠前后是发出数和收到数，单位是请求次数，不是 B。

|测量规模|每 UE 完整请求／回复|每 UE 用于时延统计|预热数量|
|---|---|---|---|
|一轮先导短测|200／200|180|20|
|一轮正式测量|2200／2200|2000|200|
|三轮正式测量合计|6600／6600|6000|600|

预热是运行前就约定的试跑部分，完整原始记录仍保留；不能事后为了让时延变小任意删包。两 UE 的“各 6600”合计是 13200 次完整事务，三 UE 合计是 19800 次；每个请求与对应回复算一笔事务，不能再乘二当作事务数。

例如“均值 1.709／1.707 ms”是 UE 1 与 UE 2 各自的平均时延，不是两轮，也不是两种负载。“6.327／6.330／6.477 ms”同样对应三个 UE，各自均值由其三轮统计样本计算。

## 重复 大包与大负载的区别

|工作|改变什么|本次是否属于这种工作|
|---|---|---|
|同条件分轮重复|相同包长、目标速率与配置下，另发一批请求|是，每轮 2200 次、前 200 次预热，每条件三轮|
|加大包长|例如数据区由 56 B 改为 256 B|否，本批始终 56 B|
|加大负载|例如保持 56 B，减小间隔，提高每秒包数|否，沿用每 UE 50 包／秒或全部 UE 合计 50 包／秒|

更长的观察不等于更大的每秒负载；三轮也不自动证明样本独立或 P99 稳定。分轮、实际间隔和慢包均保留。原生 ping 分终端自然发包，还要核对各 UE 的业务时段确实重叠；本次发现一轮无重叠后，单列保留并补同条件轮次，没有根据时延高低挑选数据。

计数与完成范围来自本项目实际实验及 TEST621。3GPP 没有规定本项目必须选择 200、2200、三轮或这些包长／业务速率；这是测量设计，新增协议公式不适用。

## 门限：什么时候允许主动给上行发送机会

**这里的门限，控制基站在暂时没有掌握终端新数据需求时，什么时候允许主动尝试给它一个小的上行发送机会。** 可以把这个机会理解为基站主动问终端：“你有没有数据要发？有的话，可以用这次安排发送。”这是帮助理解行为的比喻，实际通过上行授权安排时间与无线资源。

基站平时可以收到终端的 SR，即“我要申请上行发送资源”的请求；BSR 则报告缓存里有多少上行数据。除此以外，当前代码还可以按空闲条件主动给一个小授权。终端若正好有新包，就有机会利用这次授权发送；暂时没有业务数据时，也会消耗相应的调度和无线资源。

|当前情况|基站怎样处理|
|---|---|
|基站估计终端仍有待发数据|根据已有数据需求，进入上行调度候选|
|基站收到了 SR 请求|根据终端的请求，进入上行调度候选|
|基站暂未掌握新需求，空闲条件达到门限|可以主动尝试安排一个小的上行发送机会|

**前两种情况可以独立触发调度资格，不必先等第三种空闲门限。** 进入候选后，还要看控制资源、可用无线资源和上行时隙，才能落实为一次发送安排。

### 配置值 0 和 1 分别代表什么

|配置参数|当前代码的比较阈值|在本轮 120 kHz 配置中的换算|通俗理解|
|---|---|---|---|
|0|采用一个 TDD 周期的槽数，本轮是 5 槽|5 × 0.125 ms = 0.625 ms|主动探测更积极|
|1|采用 1 个无线帧的槽数，本轮是 80 槽|80 × 0.125 ms = 10 ms|空闲时的主动探测较保守|

**0 是代码中的特殊取值，走“按 TDD 周期计算”的分支；它没有关闭探测。1 的正值分支按无线帧数换算，所以也不是 1 ms。** 参数名为 `ulsch_max_frame_inactivity`。

例如，终端刚收到一个新包，但基站暂时还不知道它的需求：更积极的主动探测可能更早提供发送窗口，减少等待请求和授权的时间。业务未到来时，主动尝试又会占用资源。因此，我同时比较业务时延与多终端并发通信表现，而不是仅根据参数大小选择配置。

这能解释两种配置为什么值得对照。各轮的实际效果以对应实验数据为准；门限本身不是一条完整的端到端时延公式，也不是“每隔这个时间必定发一次授权”的定时器。

### 代码究竟比较了什么

实际判断来自 `gNB_scheduler_ulsch.c::nr_UE_is_to_be_scheduled`：

```text
有已知待发数据  或  收到 SR  或  内部空闲槽差达到比较阈值
```

在当前正常 CP、120 kHz 工作点，一帧 80 槽；参数大于 0 时，阈值为“参数 × 80 槽”，等于 0 时采用本配置一个 TDD 周期的 5 槽。这个换算只解释本次代码与配置，换 TDD 或 SCS 后需要重新计算。

还要保留一个实现细节：TDD 分支使用 `last_ul_frame` 和 `1 + nrofDownlinkSlots` 重建内部参考帧槽，并不总是直接使用实际保存的 `last_ul_slot`；调用侧传入的是计划上行发送的目标帧槽。因而，0.625 ms 和 10 ms 是代码比较阈值的时间换算，实际授权节奏仍要通过运行事件核验，不能直接画成严格周期发送时间表。这次只把含义解释清楚，没有修改这段 C 代码或重新发包。

授权、SR、BSR 的机制依据为 TS 38.321 V19.4.0 §5.4.1、§5.4.4、§5.4.5；槽和时间网格见 TS 38.211 V19.5.0 §4.3.2，TDD 配置字段背景见 TS 38.331 V19.4.0 §6.3.2。0／1 两个具体参数分支及内部参考槽来自本项目实际运行源的 C 实现。文献与测量边界继续参考 P01《Dissecting 5G New-Radio Latency》§III–IV、本地 PDF 第 2–4 页；教材 §13.1.1.2、本地 PDF 第 530–532 页。这里区分协议机制、代码实现和实验取值。

## 本轮所谓负载：目标每UE50包/秒

|配置|1 UE|2 UE|3 UE|
|---|---|---|---|
|每UE速率固定|50包/秒|各50包/秒，总100|各50包/秒，总150|
|总速率固定|总50包/秒|各25包/秒，总50|各约16.667包/秒，总50|

每个请求数据区56 B，等长回复另计。用十进制Mbps：

$$R_{\mathrm{UL,payload}}=N\times56\times8\times\lambda_{\mathrm{UE}}/10^6.$$

每UE50包/秒对应单UE上行请求数据区0.0224 Mbps；2/3UE总上行请求为0.0448/0.0672 Mbps。内层IPv4通常84 B，对应单UE0.0336 Mbps；不代表全部无线资源或CPU工作量。下行等长回复再按其包率计算，不能把上行单向值直接叫双向总负载。

这些包长与目标速率由本项目选择，不是OAI/3GPP默认工业流量。门限0/1只影响空闲探测资格，不等于业务速率0/1。不同工具目标间隔相同，实际发包节奏仍可能不同，结果JSON中保留实际TUN间隔。表里的1.709/1.707表示两个UE各自的时延，不是两种负载。

可将整个实验想成两套时钟：业务生成决定什么时候来包；无线调度决定什么时候给发送机会。减少空探测可能省控制资源、增加新包等待；是否有效必须同时看完成率、时延和资源开销，不能只看发包Mbps。
