# 原始源码与当前研究版本：修改、问题与影响

这页回答三个问题：**最开始的 `oi-wireless-ran` 有没有问题；研究版本具体改了什么；这些修改对时延结论意味着什么。** 本页不做新旧 ping 数值对比，也不把所有研究改动称作原源码错误。

**先说结论：120 kHz 的参数集和 0.125 ms 的标称槽长没有被判错；原 fork 确有已核实的实现缺陷和特定配置冲突。当前程序已经包含相应修正，也增加了测量和算法试验能力，但不是全部时延结果都已重测。** 能接入、能 ping，只能证明当时那条路径运行过，不能证明整个源码、所有协议配置和所有业务时延都没有问题。

本次整理只读原源码、历史 Git、原文和已完成实验；**没有修改原始 RAN，没有新启动核心网或通信实验，没有产生新的性能收益。**

### 为什么指针错误需要那个星号

`n_rb_sched` 指向调用方的“剩余 RB 数”。若调度前预算为 $B$，本次重传占用 $r$ 个 RB，调用方应该得到：

```math
B_{\mathrm{after}}=B_{\mathrm{before}}-r.
```

`n_rb_sched -= r` 改的是局部地址；`*n_rb_sched -= r` 才改该地址指向的数值。例如预算 66、已占 5，本变量应该变为 61。这是 C 调用语义和本实现的预算不变量，不是 3GPP 规定只能有 66 个 RB。频域资源位图仍有其他检查，不能从这个错误直接推出“每轮必然重复分配了资源”。

### 为什么 MAC 子头也会影响资源预算

限定普通六位 LCID、非 UL CCCH 等本次使用分支，设 MAC SDU 长度为 $L$ B，可用剩余空间为 $A$ B：

```math
h(L)=\begin{cases}2,&1\le L<256,\\3,&256\le L\le65535,\end{cases}
\qquad L+h(L)\le A.
```

子头也占 TB 空间，所以不能始终扣 3 B，也不能只修改 F 位而不修正缓冲指针和可请求字节数。例如 $A=258$ B 时最大正载荷为 255 B，$A=259$ B 时可以装 256 B。这里的 TB/MAC 开销不能与 N3 外层 IP/UDP/GTP-U 头混在一起计算。

## 4. 新增 C 探针和 Python 脚本各做什么

|部分|主要位置|用途|会不会直接证明算法降低时延|
|---|---|---|---|
|分层、RLC、UL 服务和状态观察器|`common/utils/*trace.h` 及 SDAP/PDCP/RLC/MAC/PHY 插入点|记录同包标识、入队/片段/授权/CRC/编码时刻与状态，定位等待区间|不会。它们提供证据，观察本身有开销，需要观察 ON/OFF 对照|
|RFsim 阶段观察|`ran_diagnosis.h`、`radio/rfsimulator/simulator.c`|记录样本推进、等待和混合执行区间|不会。RFsim 的样本时钟与主机时间未必 1∶1，不是真实天线测量|
|Python 运行器|`research/latency-analysis/*/prepare.py`、`run.py`|准备配置、启动/回收 gNB/UE/独立核心网、发业务、抓包、冻结输入|不是用 Python 替换 OAI 的 C 协议栈|
|Python 分析与核验|`analyze.py`、`collect.py`、独立 `verify*.py`|关联原始事务、统计时延、核校验和/字节/时间戳及生成安全汇总|只有完整实验和验证通过，才可支持明确边界内的结论|

C 仍在执行真实的 OAI 编码、协议处理和调度；Python 负责组织与分析。模型脚本另有明确理想化假设，不能当作完整 gNB＋UE 实验。探针默认关闭的路径与运行器显式开启的条件要分别看，不能只凭代码注释称“本次无观察开销”。
