## 信息确实传到了哪里

```text
私有SMF profile：5QI9 或 69，独立QFI9
  ├─ NAS：SMF→AMF的SBI抓包，PDU Session Accept中规则QFI9，显式5QI9/69
  ├─ NGAP→gNB→MAC：实际fiveqi=9/69、priority=90/5、PDB=300/60ms
  └─ N4建立请求PDI：QFI9
软件UE按QoS规则QFI9映射PDU Session/数据路径
  → oaitun_ue1 → UE协议栈 → RFsim → gNB协议栈 → N3(type1,QFI9)
  → 私有UPF → 接收应用
```

SMF到AMF的真实HTTP TCP流重组并解析multipart后，77字节NAS消息中的QoS Flow Description IE分别是`790006092041010109`和`790006092041010145`。不是仅搜索整份pcap或仅根据配置标签作判断。N4初次建立请求观察到QFI9；后续修改请求没有QFI IE，不把可选字段缺省误判成QFI0。

重要边界：原软件UE会跳过Authorized QoS Flow Descriptions的参数内容，仅保留QoS规则中的QFI与会话映射。因此本轮证明SMF发送显式5QI、gNB收到真实profile、UE规则映射与QFI9业务可用，**没有证明UE已执行完整5QI策略，也不是全部NAS/NGAP/N4一致性认证**。NAS抓包边界为SMF→AMF SBI，不冒称已解密UE空口NAS。

## 怎么算时延

应用单向时延按同一主机的单调时钟、同一编号包计算：

`L_APP(k) = [t_rx_mono(k) − t_tx_mono(k)] / 10^6 ms`。

这是发送应用记录时刻到UPF命名空间中接收应用记录时刻，包含宿主和协议栈处理，不是纯空口时间。中间段为两个实时时钟抓包点之差：

`L_TUN→N3(k) = [t_N3_wall(k) − t_TUN_wall(k)] / 10^6 ms`。

外部分段在相同wall口径下逐包满足前段+中段+后段=总wall时延；不能直接相加各段P99，也不能把中段叫纯排队/PHY时间。APP结果采用MONOTONIC，未用ping RTT替代。wall与mono总差的最大绝对偏差9/69分别为0.145891/0.022299ms，含时钟取样偏移等因素，未唯一定位原因，分段和APP口径不能混加。

路由实际核为`dev oaitun_ue1`，N3逐包PDU Session Container为UL type1/QFI9，不走同机本地路由旁路。ping只作业务前的显式状态预检，不计入UDP时延；这仍是旧UPF工程前提，非3GPP要求。

## 这次结果说明什么

本次修正已打通异质QoS所需的真实5QI来源，不再用QFI代替5QI，也不把69截断成5。这是后续多UE QUEST比较的必要前提。

69组的单次P99略高于9组，不能据此说高优先级无效或算法退化：本轮每组只有一个UE、采用PF、没有开启QUEST、没有同时争用的不同QoS UE，也没有重复反序对照。这里只报告实际功能样本，不把两组差值包装为优化收益。

尚未完成：同一小区混合5QI的多UE/反序比较、论文5QI2/84的GBR与GFBR/MFBR、TableII业务/硬件场景完整复现，以及UE完整5QI策略。现有69组将本地Non-GBR DNN profile统一设69，不能直接拿该配置声称已实现同一DNN下多UE不同5QI。新实验需独立计划和新输出，不能覆盖本轮冻结证据。
